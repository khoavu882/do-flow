`doflow config schema` lists every key with its type, allowed values, bounds, resolved default and scope, and marks each one `writable` or not. `doflow config set <key> <json-value> --layer user|project|local` writes a writable key into that layer's file after checking it the way the resolver reads it (the key's scope, its value rules, and for a `narrow-only` key that a project or local value is not wider than the layers below); `config validate` runs the same checks and writes nothing, and `config unset` removes a key from a layer. `config validate --prepared-run <file>` checks a prepared-run file the same way, one entry per fault keyed by JSON path, with no harness, model call or write: its `settings` entries are judged as `config validate <key> <value> --layer project`, and its `presets.review` and `presets.debate` must not be looser than the preset the settings give (the user, project and local files that `review --action start` reads, with the file's own `review.preset` or `debate.preset` taken as the project layer; a looser one is `not-narrower` naming the setting and its layer), and `presets.review` must also have at least the class's gate-b seat floor (the risk-policy step needs the diff and is not applied). A `config set` or `config unset` at the project or local layer may remove or lower a project's own stricter value back to what the lower layers give (for example `doflow config unset review.rounds --layer project`); that is intended, since any session may write these keys. The class seat floor in `gates.json` and its override, the preset's `rounds.min`, and the invariants are applied after the settings and cannot be lowered this way. `config set` and `config unset` refuse every security-relevant key (`autopilot.enabled`, `verify.reuse`, `workers.billing`, `guard.workerDropDatabases` and every `advice.*` key, `advice.model` included) and every `invariant.*` entry, which is locked in `core/registry/protocols.json`. A person writes a security-relevant key in the file. `advise --action configure` is that person's command for `advice.model` and is not affected. Because `advice.model` is security-relevant, an invalid `advice.model` at a layer that may widen it (the user file, or a project file) now trips `advice.enabled` to its fail-safe `false`, and `config list` exits 1 until the value is fixed. This holds for an invalid `advice.model` at any layer, including a malformed project `decision-model.json`, which now turns advice off instead of being ignored. When the user layer has already turned advice off explicitly (`advice.enabled` false), the value is the same either way (off), but the two readers name different causes: `doflow config list` credits the malformed project file as the origin of `advice.enabled` (its fail-safe) and exits 1 until the file is fixed, while `advise` reports the state as `user-disabled` and never reads the project file.

`config set` and `config unset` write one layer file at a time under a lock beside it (`<file>.lock`). A lock held by another writer is waited on for 2 s and then the write is refused with `locked`, naming the lock file and its age, nothing written. A lock is never removed automatically, whatever its age: if no writer is running, remove the lock file yourself and run the command again. A key that another `config set` wrote meanwhile is kept: when the file changed between the check and the write, the command checks again (three tries in all) before it refuses with `changed`. A write that changes an existing file first keeps the bytes it replaces in one `<file>.config.bak` beside it, replaced on each write, so a layer has at most one config backup. The check judges the bytes the writer would write: a value that would take the layer file over the reader's 64 KiB limit is refused with `too-large` and the file is left as it was. `review.rounds` below the `rounds.min` of the effective `review.preset` is refused as `not-narrower`, naming the floor, because the resolver would ignore it; under `auto` it is accepted, with a note (a text line, and `notes` in `--json`) when it is below the strictest preset's `rounds.min`.

`autopilot.enabled` is the roadmap loop's kill switch: `off` unless a person turns it on. It is global-only, so a project layer never sets it. To turn it on, write `{"schema":1,"autopilot.enabled":"on"}` into `<config home>/settings.json` yourself (`config set` refuses it: it is security-relevant). `DOFLOW_AUTOPILOT_ENABLED` accepts only the off words (`off`, `0`, `false`, `no`) and can only turn the loop off; it cannot turn it on. `src/runtime/settings/autopilot.ts` holds two readers: `readKillSwitch`, used by the roadmap loop and `orchestrate --action decide-gate --policy`, which fails to off on any doubt and counts the env off layer; and `readSeedSwitch`, used by the `roadmap seed` verb, which fails closed the other way: it refuses on any doubt, ignores the env layer, and allows only a verified durable off. The sentinel `<config home>/autopilot/off` also forces off, and a sentinel that cannot be read (any stat error but a missing file) counts as present: the loop's tripwire writes it when it sees a revert of an autopilot merge or a `merged-unverified` result, and only a person removes it. The loop and `orchestrate --action decide-gate --policy` read every layer on every call and fail to off on a missing config home or an unreadable setting. The key combines by `override`, so `doflow config -g` can show `on` while only the sentinel is set (the sentinel is listed as a shadowed candidate); the loop still stops and names `sentinel` in `annotations.switch`. Trust the loop's answer, not the `config` value.

`dispatch.fallback` accepts only `off` and `ask`, and `auto` never takes effect from settings: a user-scope `settings.json` naming `auto` is invalid and the key's fail-safe `off` applies, while a project or local file naming it is ignored and the other layers decide (default `ask`). `auto` exists only per run, and a project may only narrow the setting to `off`.

`workers.billing` is a person-written record of which headless workers have no per-run charge for your account. It has type `worker-billing`: a JSON object of 1 to 16 entries keyed by worker id (a registry harness id, for example `codex` or `antigravity`, the `agy` CLI; lowercase letters, digits and hyphens, at most 32 characters, starting with a letter). Each entry has exactly the fields `billing` (`free` or `metered`), `asserted` (a real `YYYY-MM-DD` date you state) and, optionally, `basis` (one line of 1 to 120 characters); any other field, a wrong type or an impossible date makes the whole value invalid, never a partial one. For example, `{"schema":1,"workers.billing":{"codex":{"billing":"free","asserted":"2026-10-23","basis":"flat plan"}}}` in `<config home>/settings.json`. The key is `global-only`: a project or local value is ignored and listed as `ignored-scope`, so a repository cannot widen what counts as free. The record is read from the caller's config home (`$XDG_CONFIG_HOME` or `$HOME`) and trusted as written: DoFlow does not guard who wrote that file, the same as `autopilot.enabled`. It is security-relevant with a fail-safe of invalid, so `config list` exits 1 while the record is invalid, and `config set` refuses it, so a person writes it in the file. `free` means no per-run charge for your account; a flat subscription counts, and quota limits are still handled by the fallback ladder (`dispatch.fallback`). Only `dispatch --billing-cap free` reads the record: `free` lifts a registry `unknown`, `metered` narrows, and a registry `metered` is never lifted; see the `dispatch` row in [Reference](reference.md) for the exact rule. A record naming an id that is not a registry harness is not caught by `config`; dispatch treats it as an invalid record.

`primary.harness` tells DoFlow which harness runs the primary orchestrating session (`claude`, `codex`, `opencode`, `pi`, `copilot`, `kiro`, `antigravity`), so DoFlow can distinguish the primary orchestrator from headless worker runs; `unknown` means undeclared. Default is `unknown`. It may be set through `DOFLOW_PRIMARY_HARNESS` or `config set primary.harness <id>`. Scope is `project-overridable`.

`primary.model` declares the model the main session runs (e.g. a model name string up to 120 characters), which the session hook probe checks where supported (`primaryProbe.model: payload`). Default is null. It may be set through `DOFLOW_PRIMARY_MODEL` or `config set primary.model <id>`. Scope is `project-overridable`.

`primary.onContradiction` sets what happens when the session hook observation contradicts the declared model: `warn` (default) prints a warning line on stderr, while `refuse` refuses `primary --action resolve` and `review --action start` with `primary-refused`. Scope is `narrow-only`: a project or local setting can only narrow `warn` to `refuse`, never relax `refuse` to `warn`.

`workers.enabled` is an ordered list of worker ids a run may use, optionally ending in `primary`. Scope is `narrow-only` and combine is `subset`: a project or local layer can only remove worker ids from the user's enabled list, never add new ones. When unset, all shipped harnesses followed by `primary` are enabled. It is security-relevant (`writable: false` via `config set`); write it directly into `<config home>/settings.json` after validation.

`workers.models` maps worker ids to model names by tier (`light`, `standard`, `frontier`). Tiers not listed fall back to the harness default. Scope is `global-only` and the key is security-relevant (`writable: false` via `config set`).

Before writing custom worker order and model bindings to `<config home>/settings.json`, validate the values using `config validate` with `--layer user`:
```bash
doflow config validate workers.enabled '["worker-a","worker-b","primary"]' --layer user
doflow config validate workers.models '{"worker-a":{"standard":"vendor-model-std","frontier":"vendor-model-adv"}}' --layer user
```
Once validated with no errors or warnings, save the configuration in `<config home>/settings.json`:
```json
{
  "schema": 1,
  "workers.enabled": ["worker-a", "worker-b", "primary"],
  "workers.models": {
    "worker-a": {
      "standard": "vendor-model-std",
      "frontier": "vendor-model-adv"
    }
  }
}
```

The review keys (`review.preset`, `review.rounds`, `review.sameFamily`, `review.crossFamilyRereview`) are narrow-only: a project can only make its own review stricter. `review.extraLenses` and `review.blockerClauses` are lists that add across layers and never remove. `review.rounds` unset means the preset's rounds. A looser preset setting is ignored and shown under `protocol.disagreements` in `doflow review --action start` and `doflow protocol --action resolve`. An invalid `review.*` value in the project or local file, and an unknown or invalid `review.preset` or `debate.preset` in any layer (user, project or local), is not read as the default: `review --action start` and `protocol --action resolve` refuse with `settings-unavailable` naming the key and file, `review --action check` exits 1 with `same-family-setting-unread` (for `review.sameFamily`, for a findings record that declares an `author`) or `review-preset-setting-unread` (for `review.preset`), and roadmap gate-b fails closed. A malformed user `settings.json` (bad JSON or another schema) therefore refuses review start, review check and gate-b in every project until it is fixed. When `review.preset` is not `auto`, a findings record without `protocol` is invalid (`protocol-missing` at `review --action check`, `findings-invalid` at gate-b) and is held to that preset's rounds and seats; under `auto` it stays valid. A preset added to `core/registry/protocols.json` needs no edit to `settings.json` or `telemetry.json`: the order of the `review.preset` values (`auto` ranks right after the preset of depth `deep`) and the `protocol` and `depth` vocabularies of the review telemetry line are derived from it; an unusable `protocols.json` leaves `review.preset` at `auto` and writes `protocol` and `depth` as null.

The default endpoint is the selected provider's `defaultEndpoint` in `advice.json`. `storage.retentionHours` defaults to the `lifecycle-events` bound in `storage.json`.

`advise --action configure` writes advice settings to `settings.json`; an existing `decision-model.json` is left intact and remains readable with a deprecation note. The old `prune` file is also still read with a deprecation note. Settings written by this release are not seen by earlier betas or 2.0.x; the older files are left intact for those versions.

`failure --action capture --set on|off` writes `failure.capture` in the global `settings.json`. An existing `failures/off` sentinel remains in place and still disables capture, including after `--set on`; remove the sentinel yourself to turn capture back on.

`guard.workerDropDatabases` configures a space-separated list of exact lowercase database names (`[a-z][a-z0-9_]{0,62}`, at most 32 names, at most 1 KiB, all-or-nothing); each name is at most 63 characters. A worker session may drop one listed name with a single `psql -c` or `mysql -e` command running `DROP DATABASE [IF EXISTS] <name>`. The key has `project-only` scope: set it in `<project>/.doflow/settings.json` or `.doflow/settings.local.json`; global values, environment variables, and CLI flags do not set it. At launch, the launcher resolves and validates the list from the owning project and exports `DOFLOW_GUARD_DROP_DATABASES`; the hook reads only this snapshot. An unset, empty, or invalid list grants no relaxation. The hook cannot verify which host the database client contacts.

Codex worker write access to `<project>/.doflow/settings.json` is measured only for the sandbox scope: Codex CLI 0.163 probes using `codex sandbox -P :workspace` denied the write when the project was outside sandbox-writable roots (not under `/tmp` or `$TMPDIR`, and not the command cwd), and allowed it when the project was under `/tmp` or `$TMPDIR`. The production launch flag `-s workspace-write` was not probed separately. FU-gxbryp tracks the possibility of a worker under a sandbox-writable root planting a database name for a later launch; the launch snapshot blocks self-authorization during the same run.

## Config home

DoFlow's per-machine files (`prompt-nudge`, `prune`, `decision-model.json`, `settings.json`, `failures/`, `reports/`, `session-env/`, `sessions.log`) live in one folder, `<base>/doflow`. The base is `XDG_CONFIG_HOME` when it is set to an absolute path, else `$HOME/.config` when `HOME` is set to an absolute path, else there is no config home. A relative or empty value is ignored, never read against the working directory, and DoFlow does not fall back to the account's home folder. Node code and every shell script and hook resolve it by the same rule.

With no config home, nothing is read from it, failure capture is skipped, session state is skipped (session hooks write nothing and exit 0; guard hooks still reach their own decision), and `doflow advise --action configure` without `--project` exits 2 with a usage message naming an absolute `HOME` or `XDG_CONFIG_HOME`, or `--project`.

Failure capture also reads `failure.capture` from `<config home>/settings.json` with one text rule that the dispatcher, the shell policies, the JS hook runner and Node all apply to the file's bytes up to the first NUL: every `"failure.capture": <value>` pair found must have the value `"on"`, and any other value means capture is off. JSON validity does not matter, one pair that is not `"on"` makes it off even when another says `"on"`, and a file that is not a regular file or cannot be read means off. A missing file or a file without the key leaves capture on. The environment and the `failures/off` sentinel can still only turn capture off.
