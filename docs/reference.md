# DoFlow Skills Reference

## Quick Skill Reference

| Topic | Skills |
|---|---|
| Development cycles | `/do-flow "topic"`, `/do-brainstorm "topic"` |
| Design & architecture | `/do-design "feature"`, `/do-constitution` |
| Planning & implementation | `/do-plan`, `/do-execute-plan` |
| Testing & code review | `/do-test`, `/do-code-review` |
| Analysis & diagnostics | `/do-diagnose path --focus quality\|security\|performance\|architecture` |
| Documentation & research | `/do-document path --type api\|guide\|impl\|index\|research` |

## Full Skill Reference

Arguments below mirror each skill's `argument-hint`; `test/guards/reachability.test.js` asserts they
stay in sync, so a flag documented here always exists.

| Skill | Description |
|---|---|
| `/do [command\|request] [--depth shallow\|normal\|deep] [--estimate]` | Universal dispatcher, intent routing, tool capability selection, and estimation; `/do program <goal>` researches a programme-sized ask and hands you a checked roadmap draft |
| `/do-flow [feature description] [--from brainstorm\|design\|plan\|implement\|test\|review]` | Full-cycle development: brainstorm → design → plan → execute → test → code-review |
| `/do-brainstorm [topic/idea] [--depth shallow\|normal\|deep]` | Discover requirements through Socratic dialogue; seeds requirement.md in a branch-coupled feature dir |
| `/do-design [target] [--type architecture\|api\|component\|database]` | Design system architecture, APIs, and component interfaces; writes design.md |
| `/do-plan [--depth shallow\|normal\|deep]` | Generate implementation plan and dependency-ordered task checklist; writes plan.md |
| `/do-execute-plan [--scope next\|phase:N\|all\|resume] [--review] [--scaffold]` | Execute plan.md task checklist with specialist subagents and readiness gates |
| `/do-test [target] [--clean] [--watch]` | Execute project builds, automated test suites, and coverage verification |
| `/do-code-review [target]` | Code review automation: analyze complexity, risk, SOLID compliance, and code smells |
| `/do-implement [description of the change] [--from-review]` | Direct, standalone implementation from a description or `/do-code-review` findings — no chain artifacts required |
| `/do-git [intent] [args...] [--confirm]` | Cycle-aware git operations via named intents: start, save, sync, ship, release, hotfix, backport, status |
| `/do-constitution [principle inputs] [--amend]` | Create or amend the per-repo tier-2 constitution overlay and sync impact reports |
| `/do-diagnose [target\|issue] [--focus quality\|security\|performance\|architecture] [--fix]` | Unified diagnostics, root-cause investigation, and targeted code remediation |
| `/do-document [target\|query] [--type api\|guide\|impl\|index\|research] [--depth shallow\|normal\|deep]` | Unified technical documentation, architecture indexing, and deep web research |

## Runtime & Diagnostics Commands

These are `doflow` CLI commands, not slash-command skills. Installation and lifecycle commands
(`install`, `update`, `status`, `rollback`, `remove`) are documented in [Setup](setup.md).

| Command | Description |
|---|---|
| `doflow doctor [--json]` | Health check: harness adapters, capability providers, index freshness, and the project's detected build and test commands. Health means a provider **answered a probe**, not that its binary is on `PATH` — an installed provider that cannot answer reports `UNHEALTHY`, and one that declares no probe reports `UNVERIFIED`. Its `[Runtime Reach]` section lists, per installed harness and scope, whether the skills' resolver finds a dispatcher and runtime (`REACHED`, `NO-REACH` with the install command that fixes it, or `N/A`; in `--json`, `harnesses[].reach[]`). Reach is a static check of the installed files: it does not consider the other ways the dispatcher finds the CLI (`DOFLOW_CLI`, a `node_modules` install, a `doflow` on `PATH`). Two further sections report on MCP servers and never enter `[Warnings]` or `[Findings]` (in `--json`, `mcp.servers` and `mcp.consultations`). `[MCP Servers]` lists each server a shipped stage names and, per installed harness and scope, whether it is `selected` (in DoFlow's catalog selection), `configured` (present in the harness's MCP config, whoever wrote it), `not selected`, `not taken` (the harness takes no catalog servers; both only where DoFlow read every config the harness merges) or `unknown` (DoFlow cannot see every config the harness merges, as for Claude Code and Gemini CLI, or a config it reads could not be parsed, which prints `fix <file> first`), with the command that adds it where it is missing. `[MCP Consultations]` reads this project's orchestration journals (`.doflow/state/orchestration/`) and, per stage skill, counts the servers' outcomes over the 20 most recent recorded stage runs: `consulted, used`, `consulted, nothing usable`, `skipped`, `unavailable` and `no outcome recorded`, each in its own column, and, per server and skill, lists the latest 3 runs with no outcome after their count. Only runs that recorded MCP outcomes are counted, so a stage completed before this existed never shows as missing one. Finished orchestration journals are pruned 30 days after their work finished (see the `task-orchestration` row below), so the window counts only the runs still kept. `[Decision Model]` reports the optional local decision model; `[Advice Agreement]` summarizes recorded advisory picks and outcomes. These sections do not change the exit status. Doctor reads files and starts no MCP server. The adapter line of the text output reads `adapter PASS`; the JSON gains additive fields only. Exits 1 when a provider is installed but does not answer, or a harness has `NO-REACH`; neither MCP section changes the exit status |
| `doflow capabilities [--json] [--check]` | Which provider currently backs each abstract capability on this machine. `--check` runs a deep smoke check instead of a presence check |
| `doflow enforcement --harness <id> --policy <id> [--profile <id>] [--json]` | Read the lifecycle coverage matrix and report whether the selected policy is verified to block before a tool runs; JSON includes the evidence rows, prerequisites and known gaps. Exits 0 when enforced, 1 otherwise, or 2 for usage and unknown ids |
| `doflow readiness --task-class <class> --task-id <id> [--slug <name>] [--verification-plan <text>] [--scope <text>] [--invariants <text>] [--user-decision-pending] [--json]` | Evaluate a task's readiness contract. Classes: `bug`, `feature`, `refactor`, `trivial-edit`, `dependency-change`. Returns one of four states — `READY`, `NEEDS_EVIDENCE`, `NEEDS_USER_DECISION`, `BLOCKED` — never a number. The four trailing flags are inputs the **caller states** rather than evidence the gate measured, so they are reported straight back as `callerAsserted` (JSON) and `Caller-stated:` (text), and a requirement satisfied that way links no evidence. Every call records its evaluation, whatever its state, as the task's latest record under `.doflow/state/readiness/` (in a `<slug>/` subdirectory under the same rule as evidence, described below) and prints `Recorded:` with the path; `--json` adds `record` and `declaredScope`. A `--scope` that is a comma-separated list of repository-relative paths is also kept as the task's declared scope, which `verify` bounds a change by (`Declared scope:`); any other wording stays a statement. A previous record that cannot be read is moved to `<record>.unreadable` and a `Replaced:` line says so; a record written by a newer DoFlow is never replaced. The call exits 1 when it could not record the evaluation |
| `doflow evidence --task-id <id> [--slug <name>] [--action list\|add] [--kind <k>] [--provenance extracted\|inferred\|asserted] [--provider <p>] [--capability <c>] [--locator <file[:line]\|uri>] [--content <text>] [--need <intent>] [--absence] [--batch <file>] [--json]` | List a task's recorded evidence, or record it with `--action add`: one item from the flags, or a whole stage batch from `--batch` (a JSON array, or an object whose only key is `evidence`; `--batch=-` reads stdin — the `=` spelling is required, since a bare `-` reads as the next flag). Per item `kind`, `provenance` and `source` (`--provider` + `--capability`) are required and none is defaulted; `extracted` additionally requires a locator, `inferred` and `asserted` require content, and `generated-analysis`/`user-statement` may never be `extracted`. `--need <intent>` names exactly one declared intent and stamps `source.queryRef` from the task's current plan; without it the item remains unbound. `source.attemptRef` is read from the active task attempt. `--absence` requires `--need`, takes no locator, requires `extracted` provenance, writes `result: EMPTY`, and measures freshness from the provider's index at write time. Caller-supplied `queryRef` is refused with the fix to re-run using `--need`; `attemptRef` is refused with the fix to claim the task attempt and re-run without it; `result` is refused with the fix to use `--absence --need`. Absence without `--need` asks you to name the need, a locator asks you to drop it or record a positive item, and non-extracted provenance asks you to use `extracted`. Freshness is measured at the write and never accepted from the caller. A batch is validated whole, so one rejected item writes nothing. `--confidence`, `--score`, `--relevance` and every other score-shaped flag are refused by name: relevance is a property of a search, not of a fact |
| `doflow-run render-diagrams [--slug=<slug>] [--artifact=<path>] [--format=png|svg] [--json]` (`render-diagrams.sh`) | Render a chain artifact's fenced Mermaid blocks to image files, styled by the shipped theme. A **faithful** render: same nodes, same edges, same labels, and the committed Markdown is never modified. Output lands in `<feature dir>/design/diagrams/` and is excluded from version control by an ignore rule the verb writes on first run. Requires `@mermaid-js/mermaid-cli` on `PATH`, an optional dependency DoFlow never installs: when it is absent the verb reports how to obtain it and exits 0, because it sits outside the chain and must never make a missing optional capability read as a broken run. Runs only when a user invokes it, never as part of a stage, which is why no skill names it and `test/guards/verb-reachability.test.js` allowlists the verb |
| `doflow trace [--days N] [--json]` | Trajectory of the current or most recent workflow, read from the run ledger |
| `doflow trace spans [--run <key|id>] [--json] [<project>]` | Project spans from ledger, telemetry (`runs/telemetry`), task-attempts, orchestration, worker-runs, and dispatch stores without a dedicated span store. Trace segments are scoped to task-attempt slugs rather than session run keys alone. Line placement follows tiered precedence: explicit identifiers beat time windows, an ID-less line matching multiple segments joins if it fits exactly one activity window, and lines held by a single segment join by `(run, lineage)` and window; overlapping windows remain ambiguous gaps. Emits trace spans (recorded vs derived durations) and located gaps (`unmatched`, `ambiguous`, `unparseable`) |
| `bench perf measure --paired-env <NAME=VALUE> [--surface <ids>] [--runs N] [--seed S] [--json]` | Measure latency and context budgets under alternating environment pairs (e.g. `DOFLOW_TELEMETRY=off` vs default `on`), interleaving iterations per surface to minimize drift. Refuses `--write` (exit 2) and never modifies `budgets.json`. Requires `NAME=VALUE` format with `NAME` matching `^[A-Z_][A-Z0-9_]*$`. Emits paired comparison records and delta statistics (`delta`) |
| `bench verify-baseline --snapshot <dir> [--json] [--out <dir>]` | Verification baseline computation over a recorded snapshot directory containing `manifest.json`. Validates manifest schema and runs deterministic baseline computation across recorded cases. Outputs byte-equal analysis reports (`report.json`, `report.md`); a manifest mismatch exits 1, and a missing or malformed snapshot/manifest exits 2 |
| `bench noise --iterations <a,b[,c..]> [--out <file>] [--json]` | Measure eval noise floor over k baseline repeats. Validates that iterations share the same model, commit, and case set, re-runs programmatic grading twice in memory for grader stability, and computes per-repeat means, noise, baseline mean, headroom, and a noise-check verdict. Outputs text or JSON; `--out` writes the noise artifact to the supplied path and has no default. `report` reads the baseline directory's `noise.json` by default (today this is bench/baseline/noise.json). Candidate stamps need `model` and `sourceAt`; the artifact model must match the candidate and baseline models and its case set must match `baseline.json`. With-skill runs whose skill source is not `verified` are excluded as `source-unverified` |
| `DOFLOW_TELEMETRY` | Telemetry switch (default `on`). Set to `off` to disable telemetry emission across all hook front doors, policies, and runtime components. When `off`, writers write nothing and create no files or directories under `runs/telemetry` |
| `DOFLOW_VERIFY_V0` / `<config>/verify-v0.off` | Verification V0 optimization flag (default `on`). Read once per verify invocation. When set to `off` (or when the `<config>/verify-v0.off` sentinel file exists; stat fault counts as absent/on), disables failed-first test execution and in-flight deduplication, recording `verify.run.v0="off"` |
| `doflow stats [--days N] [--json]` | Aggregate local run-ledger usage: runs per verb, failures, duration percentiles |
| `doflow indicators [--json]` | Per-stage and per-gate timings from the orchestration record, grouped by task class |
| `doflow discover [--days N] [--json]` | Missed capability opportunities in recorded runs. Exits 1 when there is a finding; an analysis it cannot settle from the recorded metadata reports `UNKNOWN` rather than "clear" |
| `doflow storage [--action report|prune|upkeep] [--json] [-g]` | Report declared stores, retention bounds and cleanup candidates, or run cleanup |
| `doflow config [list] [--show-origin] [--json] [-g] [<project path>]` | Read-only effective settings and their sources; `config set` is not supported. Exits 0 when no security-relevant setting is invalid (other invalid settings are reported), 1 when a security-relevant setting is invalid, and 2 on a usage error or unavailable settings registry |
| `doflow inventory [path] [-t <list>] [--json]` | Read-only cross-scope inventory: reads the global and the project ledger in **one** invocation and reports, per logical asset, every scope holding a copy, that copy's currency (`matches`, `diverged`, or `indeterminable` — the third means this scope holds no basis for judging the copy at all, whether because no fingerprint is recorded for it, because the scope's plan would remove it rather than rewrite it, because no plan was produced for that harness, or because the recorded row names no harness or no ownership identity — the two components the plan lookup is keyed by, so no planned change could ever be found for it; each copy states which, and none of the four is a weaker `diverged`), the precedence verdict naming the scope whose copy the harness loads, and any unmanaged file sharing a directory the harness loads wholesale. The verdict is derived from the harness's recorded order **and** resolution mode together (`core/registry/harnesses.json`), never from either alone, and is **withheld with its reason** where the mode is unestablished rather than defaulted to a guess. It states its own repair coverage: only a divergence is reachable by `doflow reconcile`, and a shadow, a withheld verdict, a copy nothing judged and an unmanaged file are each reported as having no remedy from it. A scope with nothing recorded is reported as holding nothing — the ordinary state of a repository never installed into — and is never an error. Takes no scope flag: reading both scopes is the whole point, so `-g` is refused rather than silently narrowing the answer. Exits 1 when there is any finding, including a withheld verdict or a copy this scope holds no basis for judging, because the caller cannot conclude the install is sound from either; 2 only when the registry, a ledger or a named harness cannot be resolved. Writes, moves and deletes nothing — the remedy on each entry is text to run, and the verb never runs it |
| `doflow classify --task-class <id> [--calling-skill <skill-id>] [--rationale <text>] [--proposed-by <who>] [--request <text>\|--request-file <path>] [--json]` | Validate a proposed task class against the workflow registry and return its workflow. A class the registry does not declare is **rejected** with the valid set and a suggestion — never coerced to `feature`. With `--calling-skill`, it also checks that the class's workflow has a stage the caller can occupy, and rejects it when it does not; without it, fit is reported as `NOT_EVALUATED` rather than assumed. Optional `--request` or `--request-file` asks the configured local decision model for an advisory second opinion; the verdict and exit status are determined before that call and never change because of its answer. Exits 1 on a rejection, 2 when no class was proposed |
| `doflow workflow --task-class <id> [--json]` | Resolve a class to its ordered stages, their gates, which stages mutate source, and which readiness templates gate them. Exits 2 on an unknown class |
| `doflow orchestrate --action start\|status\|catch-up\|handoff\|complete-stage\|skip-stage\|decide-gate\|annotate --task-id <id> [--task-class <c>] [--stage <id>[,<id>…]] [--gate <id>] [--node <id>] [--decision approve\|reject] [--policy <gate>] [--note <text>] [--reason <text>] [--forced] [--mcp-outcome <server>=<outcome>]… [--verification-plan <text>] [--scope <text>] [--invariants <text>] [--json]` | Deterministic run-state machine over a class's stage list. `start` compiles the program; `catch-up` positions the run toward one or more comma-separated candidate stage ids, backfilling non-mutating stages/gates it walks past (marked `backfilled: true`) and refusing a candidate id the run's own compiled program doesn't contain (the class's workflow, when no run exists yet); each completed or skipped (optional-only) stage advances a persisted cursor under `.doflow/state/orchestration/`; gates pause the run (`AWAITING_GATE`) until approved or rejected, never auto-approved regardless of kind (the one machine decision is `decide-gate --policy`, below, which approves only on evaluated facts and records its decider as `autopilot`); `annotate` appends a history entry without touching cursor/state, for a stage re-run after its own handoff; `handoff` and `complete-stage` of a source-mutating gated stage (the `implementation` stage of `feature`, `bug`, `refactor`, `dependency-change` and `trivial-edit`) need a READY readiness record of the stage's template, made by `readiness` before the call (a `--task-class` that differs from the run's own is refused). Without one the call refuses before changing anything, names the `readiness` command that clears the refusal and says which harnesses also check at edit time; nothing is evaluated by the call, so `--verification-plan`, `--scope` and `--invariants` are not read and a note says so. The record and the run are looked for in this checkout, else in exactly one other checkout of the repository for the same feature, and a run found there is updated where it is. `--forced` requires `--note` and is refused on any action but `decide-gate`/`annotate`. Every transition is journaled — runs survive process death. Transition refusals exit 1 naming the expected node. `--mcp-outcome` (handoff only, repeatable, one server per value; any other action refuses it with exit 2) records what the stage did with an MCP server it names: `<server>=used`, `nothing-usable`, `unavailable` or `skipped:<reason>` (a reason of 1 to 120 characters, no comma). The handoff then adds `consultations` (the stored record: the servers the stage names, one outcome per server and where it came from; `null` for a deferred handoff) and `mcpWarnings` (an array of `{kind, server?, taskId?, text}`) to its `--json` snapshot. A named server with no outcome from the flag, from the `Tools used:` line of a task report, from evidence attributed to that server or from the install facts prints `[WARN] mcp: <skill> recorded no outcome for <server>; pass --mcp-outcome <server>=used\|nothing-usable\|skipped:<reason>\|unavailable` on stderr; an `unavailable` outcome prints `[INFO] mcp: <server> unavailable to <skill>; add it: <command>` on stdout; a malformed value is ignored with a warning. A standalone handoff prints the same lines and stores nothing. None of these changes the exit status. `decide-gate --policy <gate>` lets the runtime decide instead of a person: `--gate` must name the same gate, and `--decision`, `--forced` and any caller-named decider (`--by`) are refused with exit 2 before any state is read, as is the reserved decision channel `policy` on every other verb. The policy is read from develop's committed head, never from the feature branch (`core/registry/gates.json`, narrowed at most by `.doflow/gates.override.json` in the main checkout), and the facts each predicate names are gathered with a locator and sha256. When every predicate passes the gate is approved, and the decider is recorded as `autopilot` with the policy id and digest and the inputs in the run history and as a `policy`-channel entry in the feature's decision register. A deny changes nothing: the run stays `AWAITING_GATE`, autopilot never rejects, and the answer carries `decision: "deny"` with `reason`, `reasons` and `rule`; the call still exits 0, so callers branch on `decision`, not on the exit code. With `autopilot.enabled` off on any layer the call denies `autopilot-disabled` before reading any fact. From a linked worktree the run is created and read in the main checkout's `.doflow/state` (see [Where a task's records live](#where-a-tasks-records-live)). |
| `doflow research-request --task-id <feature-id> [--slug <name>] [--action open\|list\|resolve] [--stage-id <stage-id>] [--question <text>] [--reason user-request\|detected-gap\|ideation] [--blocking true\|false] [--request-id <id>] [--outcome answered\|unresolved] [--claim-id <id>] [--evidence-id <id>] [--gap <text>] [--json]` | Stage-scoped external research on an existing feature run. `open` requires the current stage, a question and reason (detected gaps block by default); `list` is the default; `resolve` requires an open request and either a supported same-task claim with linked extracted external evidence for `answered`, or an explicit gap for `unresolved`. A blocking open/unresolved request refuses completion of its stage without moving the workflow cursor; research never approves a gate. The `ideation` reason is valid only on a feature discovery or design stage and is non-blocking by default, but an OPEN ideation request refuses completion of its stage until it is resolved. Web and Context7 retrieval remain in the harness, not this runtime. Requests, and the run and claims they are checked against, are read and written in the same root: the main checkout's `.doflow/state` from a linked worktree. |
| `doflow task-attempt --action claim\|finish\|release\|status\|start\|pause\|cancel\|resume\|inspect\|reopen\|report-usage --slug <name> [--task <id>] [--owner <name>] [--mode manual\|sequential\|subagent] [--owner-override <reason>] [--epoch <n>] [--reserve-tokens <n>] [--exec-worktree <path>] [--token <n>] [--result COMPLETED\|BLOCKED\|ABANDONED\|INCONCLUSIVE\|FAILED] [--evidence-id <id>] [--reason <text>] [--tokens <n> --tokens-basis measured\|estimated] [--by <name>] [--budget-attempts <n>] [--budget-tokens <n>] [--adopt-unowned] [--ack sha256:<hex>] [--json]` | The attempt ledger for a feature's plan tasks, one record per clone shared by its linked worktrees (`.doflow/state/task-attempts/<slug>.json` under the main worktree). `claim` grants one active attempt per task with a monotonic fencing token and refuses with `active-attempt`, `already-done`, `unknown-task`, `unmet-phase` (a task in an earlier phase has no COMPLETED attempt), `unmet-dependency`, `dependency-held`, `budget-exhausted`, `cancelled`, `run-paused`, `run-cancelled`, `reservation-required`, `aggregate-unaccounted` or `aggregate-exhausted` in every plan; concurrent claims yield exactly one `claimed`. `finish` and `release` apply only to the active token and otherwise return `stale`; `finish` also refuses with `plan-changed` when the task's `plan.md` line changed since the claim, and `finish --result COMPLETED` needs `--evidence-id` naming an active, non-stale `test-result` whose observation exited 0, is bound to the feature slug or the task id, and was observed no earlier than the attempt started. `status` reports `complete` only when every plan task has a COMPLETED attempt; a task ticked `[x]` without one is listed in `unclaimedChecked`. There is no lease or heartbeat: a crashed claimer is recovered by an explicit `release`. `orchestrate` refuses to complete the `do-execute-plan` stage while a ledger exists and is incomplete, and records the stage as `unverified` when the feature has no ledger. With a `**Task graph:** v1` plan, `claim` also refuses `owner-mismatch` (unless `--owner-override <reason>`), `resume-required` (an `--epoch` other than the run's) and `worker-session`; `--reserve-tokens` holds tokens against the run's budget and `--exec-worktree` (an existing directory, else exit 2 `usage`; 080 DEC-023) names where the attempt runs. `finish` and `release` take `--tokens <n> --tokens-basis measured\|estimated` together, as the caller reports them, and `finish --result FAILED` needs `--reason`. `report-usage --task --token --tokens --tokens-basis` sets the usage of an ended attempt that has none and refreshes its run's totals, in any plan; it is fenced by the token alone, so a worker may report, and it is the remedy for `aggregate-unaccounted` (080 DEC-018). It returns `usage-recorded`, and refuses `unknown-task`, `stale no-attempt` (no attempt has that token), `active-attempt` (finish it instead), `stale attempt-cancelled` (its reservation already counts as estimated) or `usage-present` (it never overwrites). The run controls act on the caller's run, each needs `--by <name>`, and each refuses `worker-session` in every plan and `identity-solo`; `resume` refuses `identity-solo`, and `worker-session` in a graph plan only (080 DEC-022): `start` (optional `--budget-attempts`, `--budget-tokens`, each at least 1; refuses `run-exists`), `pause --reason` (claims refuse until an acknowledged resume; active attempts still finish; refuses `control-unchanged`, `run-cancelled`), `cancel --reason` (one attempt with `--task --token`, else the whole run, with `--adopt-unowned` to take attempts that carry no run; marks attempts and ends no process; one attempt refuses `no-active-attempt`, `token-mismatch` or `foreign-run`, an already-cancelled run `control-unchanged`) and `reopen --task --token --reason` (the done attempt becomes superseded; refuses `not-done`, `token-mismatch`, `run-cancelled`). `resume` without `--ack` writes nothing and returns `ack-required` with the report and its digest; `resume --ack <digest> --by <name> [--reason]` resumes with a new epoch, or refuses `report-changed` with the fresh report when the digest no longer matches. `inspect` is read-only: the graph, every task's state and budget, and the caller's run with recomputed totals. A flag given to an action that does not take it is exit 2 `usage`, and an integer flag is digits only (`5abc` and `-1` are usage; `--epoch` and the budgets also refuse 0). Exits 0 applied (`claimed`, `applied`, `released`, `started`, `paused`, `cancelled`, `resumed`, `reopened`, `usage-recorded`) or a `status`/`inspect` read; 1 `refused`, `stale` or `ack-required`, with the disposition in the JSON on stdout; 2 malformed input or an unreadable store or plan (a torn or future-version file is left unchanged). Exit 1 with no JSON on stdout is a parser usage error (for example `--reason` with no value, or a flag a pre-080 runtime does not know): nothing ran. `delegated-A` or `delegated-B`) and, on coordinator-served classes, `rawValidity.semanticReached` (the count of answers whose
semantic leg answered); each absolute gate row (not the relative C versus B or A rows) carries `excluded`, the C class rows it covered but did not count,
with a reason.

`readiness`, `evidence`, `claim`, `context-pack`, `retrieval-plan` and `outcome` read per-project
state under the invoking repo's `.doflow/state/` (from a linked worktree, the main checkout's; see
[Where a task's records live](#where-a-tasks-records-live)); run them from the project the task belongs to,
or pass `-g` for the global scope. Those verbs and `research-request` accept `--slug`; for a
feature with a decision register their records live in a `<slug>/` subdirectory of each store, as
`.doflow/state/evidence/<slug>/<task>.json` (claims are `evidence/<slug>/<task>_claims.json`), so the
same task id in two features no longer collides. A feature without a register, and a task id equal
to the slug, keep the flat `.doflow/state/<store>/<task>.json` path. Every verb that takes `--slug`
(these, plus `verify`, `scaffold`, `decision`, `orchestrate`, `validate`, `prereqs`, `render-audit`,
`task-brief` and `parallel-check`) refuses an unsafe one with exit 2 and `{"error":"invalid-slug",...}`. `capabilities` reports on the machine and is
scope-independent; `doctor` reports on both, so index freshness and command detection follow the
same project scope.

### Where a task's records live

`evidence`, `claim`, `readiness`, `context-pack`, `research-request`, `outcome`, `retrieval-plan`,
`retrieve` (when it has a `--task-id` or `--slug`) and `orchestrate` read and write a task's records in
one root. Run from a linked worktree they always use the main checkout's `.doflow/state` (the first
entry of `git worktree list`), whatever folders the worktree holds, so one task's records are never
split across two stores. This also holds for a project that tracks `agent-docs/`; before feature 115 a
worktree was redirected only when it lacked the feature folder. Delivery records (`delivery/`) and the
orchestration run (`orchestration/<slug>.json`) follow the same root, and `render-audit` reads the run
from the main checkout. A DoFlow sandbox checkout (`.doflow-worktree-base` at its root) keeps its own
store, and `-g` keeps the home store. When a feature slug resolves, a redirected call prints one stderr
note, `feature '<slug>' lives in the main checkout <root>; this task's records are read and written there`.

Source files stay in the checkout the verb runs in: `context-pack` reads the feature folder, plan and
pointers there, and a relative evidence `locator.file` is resolved and its freshness hash taken there
(a file that exists only in the main checkout, such as a feature folder not yet in the worktree, is read
from it). Only the records move.

Records the task already holds in the worktree's own `.doflow/state` are adopted on the first call that
carries a `--task-id`: each is moved to the same path in the main checkout under that file's lock, and
the worktree copy is deleted once the move succeeded. The stores adopted are the ones
`core/registry/storage.json` lists with `src/runtime/state-root.ts` among their writers (evidence and
claims, delivery, readiness, research requests, outcome, retrieval plan, orchestration run). A file
present in both checkouts with different bytes refuses the call with exit 2 and
`{"ok":false,"error":"store-conflict","paths":[<main file>,<worktree file>]}` (without `--json`, one stderr
line naming both); nothing is moved, so keep one copy, remove the other and run the call
again. Equal bytes just delete the worktree copy.

`doflow-run paths --json` carries one more key, `feature_root`: the checkout that holds
`agent-docs/doflow/<slug>`, the current checkout when it has the folder, else the main checkout when the
folder is only there, else the current checkout (a new feature, or a slug that names no feature).
`repo_root` keeps meaning the current checkout, and every emitted artifact path stays relative to it.
`validate` reads default targets, `render-audit` writes `audit.md` and the `decision` verb resolves the
feature folder under `feature_root`. `validate` also checks each `plan.md` with the `task-graph` rule:
one finding per problem `plan-check` reports (for example a duplicate task id, an unknown dependency or a
cycle). It prints one `note:` line on stderr and adds no finding when the dispatcher, Node or `jq` is
unavailable.

`--task-id` and `--task-class` are **required**, not defaulted. Readiness, evidence, claims and a
context pack all belong to one named task under one named contract; substituting `default` or
`feature` for an argument the caller omitted produces a confident verdict about a task or a
contract nobody asked about, which is exactly the failure mode the runtime is being corrected for.
Every refusal names the valid set.

An evidence `--kind` is one of ten: `exact-search`, `semantic-retrieval`, `structural`,
`historical`, `documentation`, `test-result`, `runtime-observation`, `user-statement`, `diff`,
`generated-analysis`. An unknown one is refused with all ten named. The ledger mints the record's
`id` and measures its `freshness`, so neither is accepted from the caller, and `supports` /
`contradicts` belong to `claim --action link`, which updates both sides of the relationship rather
than leaving a claim unaware of the evidence pointing at it.

Every command in this table is also a verb on the runtime seam — `doflow-run <verb>` — which is how
skills reach them. The two spellings run the same implementation; the seam additionally records a
metadata line in the run ledger.

`indicators` reads a different file from the three below it: the per-task orchestration records at
`<config>/state/orchestration/<slug>.json`, which the workflow orchestrator writes as stages complete.
That is why it is a separate verb rather than a mode of `stats` — a run-ledger record names no task,
stage or class, so no extension of `stats` could group by any of them. It reports per-stage intervals,
gate waits charged to no stage, recorded stage outcomes and rerun counts, grouped by task class, and it
prints what it cannot measure: anything needing git, pull-request or CI data, and the fact that a stage
figure is an interval since the previous recorded event rather than pure execution time. It writes
nothing.

`trace`, `stats` and `discover` read the run ledger at `<config>/state/runs/YYYY-MM-DD.jsonl`,
which `doflow-run` appends to once per dispatched verb. They locate it the way the dispatcher does
— nearest `.doflow` walking up from the working directory, or the global one — so they work from a
subdirectory. The walk passes over a `.doflow` inside another `.doflow` (a dispatch worktree's) and
continues to the project's store; that worktree `.doflow` used to hide the project store because the
launch writes the worker's delivery pack into its own `.doflow/state/delivery`. Records are metadata
only: a verb, a capability, a provider, an exit code, a
duration, counts and byte volumes. No argument value, command output or file content is recorded.
An empty ledger is a normal state and is reported as "no conclusion can be drawn", never as a
clean bill of health.

`inventory` reads neither the run ledger nor the orchestration record: it reads the two *ownership*
ledgers, one per scope, and derives everything else at read time. Nothing it reports is persisted.
Its optional positional is the project root (default the working directory) and `-t` restricts it to
named harnesses; the global scope's root comes from the process home directory and is not an
argument. Its report and `doflow reconcile` deliberately disagree about how much is repairable —
`reconcile` converges a scope onto what `doflow.lock` pins and names a harness the ledger holds and
the lock lacks — so the report states that gap as repair coverage rather than hiding it by adopting
the narrower definition. The modules behind it live under `src/runtime/inventory`.

`scaffold` resolves which feature is active the same way every chain skill does — from the working
directory, branch-derived in a git repo — so run it from the project root. Where a non-git root
holds more than one feature directory it cannot choose: it exits 2 naming every candidate, and
`--slug <name>` re-runs against the one you pick.

**Dense/rerank retrieval slots.** `core/registry/models.json` accepts an optional top-level `slots`
array binding a retrieval stage (`dense` embedding lookup, `rerank` cross-encoder pass) to one
declared provider: entries are `{ "id": "dense" | "rerank", "provider": <models.json provider id>,
"model": "<concrete model>", "enabled": false }`. A slot changes nothing until it is both declared
and `"enabled": true` — until then (and whenever the bound backend does not answer a PATH probe)
retrieval stays lexical BM25 plus the import graph, which remains the correctness floor. There is
deliberately no HTTP client here: enabling a slot only routes lookups to the named provider through
the same advisory availability probe `model-role` uses; the provider implementation itself (local
vs API) is a separate decision and no caller invokes one today. Malformed slots fail registry load
loudly rather than reading as "no dense provider".

### Storage stores

Roadmap `next` holds `.doflow/state/roadmap/lease.json` for one call, keeps one record per run in

been reused, unreadable contents) is never taken over: every call answers `lease-held` until a

every step boundary and stops with `lease-lost` when it no longer holds this call's own bytes.

and reports `merged-unverified` when no clean PASS verify record for the row on the new develop head answers the post-merge check (the `roadmap` row above states the rule).

cleanup.

`.doflow/state/verification/runs/<taskId>.jsonl` in the repository's main checkout, the lifecycle project root, whichever checkout it ran in (store

`autopilot.enabled` is the roadmap loop's kill switch: `off` unless a person turns it on. It is global-only, so a project layer never sets it. To turn it on, write `{"schema":1,"autopilot.enabled":"on"}` into `<config home>/settings.json` yourself (`config set` is not supported). `DOFLOW_AUTOPILOT_ENABLED` accepts only the off words (`off`, `0`, `false`, `no`) and can only turn the loop off; it cannot turn it on. `src/runtime/settings/autopilot.ts` holds two readers: `readKillSwitch`, used by the roadmap loop and `orchestrate --action decide-gate --policy`, which fails to off on any doubt and counts the env off layer; and `readSeedSwitch`, used by the `roadmap seed` verb, which fails closed the other way: it refuses on any doubt, ignores the env layer, and allows only a verified durable off. The sentinel `<config home>/autopilot/off` also forces off, and a sentinel that cannot be read (any stat error but a missing file) counts as present: the loop's tripwire writes it when it sees a revert of an autopilot merge or a `merged-unverified` result, and only a person removes it. The loop and `orchestrate --action decide-gate --policy` read every layer on every call and fail to off on a missing config home or an unreadable setting. The key combines by `override`, so `doflow config -g` can show `on` while only the sentinel is set (the sentinel is listed as a shadowed candidate); the loop still stops and names `sentinel` in `annotations.switch`. Trust the loop's answer, not the `config` value.

The default endpoint is the selected provider's `defaultEndpoint` in `advice.json`. `storage.retentionHours` defaults to the `lifecycle-events` bound in `storage.json`.

`advise --action configure` writes advice settings to `settings.json`; an existing `decision-model.json` is left intact and remains readable with a deprecation note. The old `prune` file is also still read with a deprecation note. Settings written by this release are not seen by earlier betas or 2.0.x; the older files are left intact for those versions.

`failure --action capture --set on|off` writes `failure.capture` in the global `settings.json`. An existing `failures/off` sentinel remains in place and still disables capture, including after `--set on`; remove the sentinel yourself to turn capture back on.

`guard.workerDropDatabases` configures a space-separated list of exact lowercase database names (`[a-z][a-z0-9_]{0,62}`, at most 32 names, at most 1 KiB, all-or-nothing); each name is at most 63 characters. A worker session may drop one listed name with a single `psql -c` or `mysql -e` command running `DROP DATABASE [IF EXISTS] <name>`. The key has `project-only` scope: set it in `<project>/.doflow/settings.json` or `.doflow/settings.local.json`; global values, environment variables, and CLI flags do not set it. At launch, the launcher resolves and validates the list from the owning project and exports `DOFLOW_GUARD_DROP_DATABASES`; the hook reads only this snapshot. An unset, empty, or invalid list grants no relaxation. The hook cannot verify which host the database client contacts.

Codex worker write access to `<project>/.doflow/settings.json` is measured only for the sandbox scope: Codex CLI 0.163 probes using `codex sandbox -P :workspace` denied the write when the project was outside sandbox-writable roots (not under `/tmp` or `$TMPDIR`, and not the command cwd), and allowed it when the project was under `/tmp` or `$TMPDIR`. The production launch flag `-s workspace-write` was not probed separately. FU-gxbryp tracks the possibility of a worker under a sandbox-writable root planting a database name for a later launch; the launch snapshot blocks self-authorization during the same run.

### Config home

DoFlow's per-machine files (`prompt-nudge`, `prune`, `decision-model.json`, `settings.json`, `failures/`, `reports/`, `session-env/`, `sessions.log`) live in one folder, `<base>/doflow`. The base is `XDG_CONFIG_HOME` when it is set to an absolute path, else `$HOME/.config` when `HOME` is set to an absolute path, else there is no config home. A relative or empty value is ignored, never read against the working directory, and DoFlow does not fall back to the account's home folder. Node code and every shell script and hook resolve it by the same rule.

With no config home, nothing is read from it, failure capture is skipped, session state is skipped (session hooks write nothing and exit 0; guard hooks still reach their own decision), and `doflow advise --action configure` exits 2 with a usage message naming an absolute `HOME` or `XDG_CONFIG_HOME`.

Failure capture also reads `failure.capture` from `<config home>/settings.json` with one text rule that the dispatcher, the shell policies, the JS hook runner and Node all apply to the file's bytes up to the first NUL: every `"failure.capture": <value>` pair found must have the value `"on"`, and any other value means capture is off. JSON validity does not matter, one pair that is not `"on"` makes it off even when another says `"on"`, and a file that is not a regular file or cannot be read means off. A missing file or a file without the key leaves capture on. The environment and the `failures/off` sentinel can still only turn capture off.

## Hook envelope and migration notes

Shipped hook bridges decode native events into envelope v1, call a canonical policy and render the harness's native response. The versioned coverage block in `core/registry/lifecycle.json` records policy, harness, event, profile and evidence; `doflow enforcement` reports what that evidence supports.

### Envelope, decision and diagnostics

Envelope v1 is the object under `doflow_event` in the native payload. It carries `version: 1`, the registry harness id, the native event name verbatim and a canonical operation; tool, paths, command, patch, correlation and identity fields appear only when the native input supplies them. `projectRoot` is reserved for a launcher and is never inferred from native `cwd`. Policies read v1 only; every other version is unsupported, and no native-field fallback remains. A direct policy caller must send v1 or pipe its native payload through `bash .doflow/shared/hooks/bridge/bridge.sh <harness> <event> <policy>`.

When `DOFLOW_DECISION_FD` names an open single-digit descriptor from 3 through 9, each policy writes a compact version-1 record on that descriptor: `v`, `policy`, `policyVersion`, `outcome` and `code`. The provisional allow record comes first; the last record determines the policy outcome. With the variable unset or an unusable descriptor, no record is written. Records contain no free text.

`DOFLOW_FAULT_PROFILE` selects `compat-1` (default) or `strict-1`; an unknown value uses `compat-1` and records `fault-profile-unknown`. Compat preserves each front door's current effect. Strict blocks faults for blocking policies, except Stop faults, which remain non-blocking under both profiles; a real Stop deny still blocks (DEC-039). `DOFLOW_BRIDGE_TRACE`, when set to a file path, appends the bridge's decision object there; it is not model-visible. `DOFLOW_RUN_ID`, `DOFLOW_ATTEMPT` and `DOFLOW_TASK_ID` are reserved inputs for a launcher: in 077 they populate envelope identity or task fields when supplied and are otherwise absent. `DOFLOW_SESSION_ROLE` is normalized case-insensitively: unset or empty means `main`, `worker` means `worker`, and any other value emits a warning and is treated as `worker` by session policies; the envelope includes the role only when the supplied value is exactly `main` or `worker`.

Bridge diagnostics use the existing failure store and leave its storage declaration unchanged. Bridge failure-store points include `eval-error:exit-2-unmarked`, `eval-error:exit-<n>`, `eval-error:signal-<NAME>` (not SIGTERM, SIGINT or SIGPIPE), `bridge-spawn`, `bridge-timeout`, `bridge-missing`, `envelope-missing`, `contract-missing`, `envelope-encode` and `fault-profile-unknown`. The Antigravity runner records `runner-event-missing` when its event argument is missing or unknown. A `decision-mismatch` appears in the decision object and bridge trace only; it is a policy contract bug, not a failure-store point (DEC-028). Policies may record `unsupported:envelope-version`, `edit-without-target`, `dependency-missing:jq` and their existing policy-specific points. Diagnostic messages remain empty.

### Migration notes

The legacy native-field decoder has been removed. This is a breaking change for scripts that
pipe native payloads directly to a policy: update them to send a v1 envelope or use the bridge
command above. Input without a v1 envelope is out of step. The gate, bash and MCP policies deny
with `[<policy>] DoFlow hooks out of step; run: doflow update -t <harness>`; Stop and context
policies exit silently, with the prompt hook's `{}` no-op. If a door cannot load the bridge, it
uses a fixed native out-of-step response.

When an install or update changes shared hooks, it also refreshes outdated hook front doors for
other installed harnesses at that scope. Install/update plans report companion refreshes,
including harnesses the command did not name; dry-run lists them too. Edited
companion doors refuse the plan unless `-f` is supplied. The single backup includes companions,
and `doflow rollback <id>` restores them with the shared tree. On installs made before 077, Codex
and Gemini hook scripts have no ledger rows, so an edited script is replaced on the first update,
not refused. That update's backup keeps the edited copy for `doflow rollback <id>`; subsequent
edits are detected and refused. Antigravity shims are always overwritten and have no edited-door
check.

The Antigravity plugin bundle no longer declares hooks because its old entries pointed at files
the Antigravity projection does not install. Its skills, rules, agents and MCP configuration
remain available. The runner's unused Gemini-specific agent branch has also been removed.

Compared with the 0fcd973 front doors, the shared bridge intentionally changes these cases:

- A missing policy file is an evaluation error: `compat-1` proceeds and records a diagnostic; `strict-1` denies (DEC-025). Previously the shell's missing-file exit 127 could accidentally deny.
- The bridge captures policy output without a temporary file; an unwritable `TMPDIR` does not turn a gate deny into an allow. Background jobs close inherited bridge descriptors, so they do not hold Stop or SessionStart open. In `strict-1`, missing `jq` still produces the native deny; `compat-1` keeps its allow behavior (FX.1–FX.3).
- Codex `update -t codex -f` re-merges edited `hooks.json`, preserving user entries. Without `-f`, the conflict remains and the message gives a working remedy (DEC-040).
- A blocking evaluation error renders `[<policy-id>] DoFlow policy error; details: doflow-run failure list` on stdout (IC-013/DEC-019), rather than exposing raw policy or runtime stderr as the reason. Kiro PreToolUse and Stop doors use stderr for the fixed reason where their native contract requires it; Claude Stop retains its original exit code. Codex Stop crash stderr is suppressed (DEC-037).
- Context and advisory policy faults render nothing to the model and record a diagnostic (DEC-022).
- Codex `subagent-audit` now prints nothing for an error outcome; previously it printed `{}` when the policy failed.
- Kiro's agent-config event names (`agentSpawn`, `preToolUse`, `stop`) resolve to the same effects and native responses as their hook-config aliases (`SessionStart`, `PreToolUse`, `Stop`); the envelope retains the native event name.
- Antigravity's runner decodes its routed command, MCP and edit tools in the shared envelope path. Under RA1, `apply_patch` with `AbsolutePath` is now denied when design artifacts are absent; the legacy matcher allowed it.
- A policy terminated by a signal on a pass-through door exits with status `128+n` (128 plus the signal number), such as `139` for SIGSEGV. Blocking doors render their native deny response instead.
- A missing v1 envelope or contract is an out-of-step state: gate, bash and MCP policies deny
  with the update command; Stop and context policies exit silently (DEC-032, DEC-033).
- A missing bridge file makes a shell door render its fixed native out-of-step response. The Pi
  extension blocks with the fixed native out-of-step reason; its coverage is blocking only for the
  live-observed `cli-extension` pre-implementation gate row. Project-interactive and
  user-interactive rows remain unknown; the live record does not establish interactive loading or
  project-trust behavior (DEC-036). The Antigravity runner applies this rule for a missing
  bridge under every fault profile: its gate denies and Stop stays silent (DEC-035).
- The bridge preserves a caller-set, non-empty `DOFLOW_AGENT`; otherwise it sets the harness id.

## Storage and retention

DoFlow prunes what it writes by default. A pass runs silently after a runtime verb (at most once a day per root), after `verify`, after `install` and `update`, and from the session hooks of harnesses that have them. It removes only entries of finished work past the bound in the table above, never open, waiting or unfinished work, stops after 750 ms or 5,000 removals and continues on the next pass. A pass never changes a command's output or exit status.

### Reading `doflow storage`

```bash
doflow storage                    # report: every store, its entries, size, bound and what a pass would remove
doflow storage --json             # the same as JSON, with the effective setting and the file that decided it
doflow storage --action prune     # run one pass now, ignoring the daily throttle
doflow storage -g                 # user and machine roots only
```

The report changes nothing on disk. It prints one line `Settings: project <on|off> (<file>|default); user <on|off> (<file>|default)`, naming the `prune` file that decided each setting, then one block per store: its `id`, `Location:`, `Entries: <n>; size: <bytes> bytes`, `Bound:` and `Would remove: <n>`, with up to 20 of those names followed by `... and <n> more`. `--action prune` prints the same and ends with `storage: removed <n> entries`. `--json` adds each store's `failed` entries, each with a `code`; `link-in-record-store` means a work record store holds a link, so log protection could not be checked and that pass removes no logs. `--action upkeep` is what the session hooks run: it prints nothing and always exits 0.

### Switching pruning off

`storage.prune` in the applicable `settings.json` decides whether pruning runs. Set it to `"off"` in `<project root>/.doflow/settings.json` for that project's stores, or in `<config home>/settings.json` for user and machine stores. A project value applies only to project roots. Use `doflow config list --show-origin` to see which file decides the value; `config` is read-only.

The legacy one-line `prune` files remain readable when the corresponding settings key is absent, and `doflow config list` reports them with a deprecation note:

| Scope | Path |
|---|---|
| project | `<project root>/.doflow/prune` |
| user | `<config home>/prune` |

The first line, trimmed and lowercased, must be `on` or `off`. For project roots the project file decides when present, else the user file; user and machine roots read the user file only. A legacy file that cannot be read, is empty or holds anything else counts as `off`; with neither settings key nor legacy file present pruning is `on`. For lifecycle-event retention, an explicit `DOFLOW_RETENTION_HOURS` takes precedence over `storage.retentionHours` in a settings file. If the environment value is unset, an explicit settings-file value still applies while pruning is off; with neither explicit value, the registry default applies only while pruning is on. An invalid `DOFLOW_RETENTION_HOURS` is reported as invalid and does not fall back. `storage --action prune` reports whether pruning is off and whether the explicit retention window removed lifecycle events. The report still lists what a pass would remove from other stores; for lifecycle events it lists only what an explicit environment or settings-file value would remove. The ignore file below is still written, and `existing` stores keep their own behaviour.

### The state ignore file

DoFlow writes `.doflow/state/.gitignore` (and `~/.doflow/state/.gitignore`) when the folder exists and holds no `.gitignore`:

```
# DoFlow runtime state: local to this machine, kept out of git by DoFlow.
# Removed by `doflow remove` when DoFlow leaves this project.
*
!/ledger.json
```

`git add -A` then stages nothing under `.doflow/state/` except `ledger.json`, while `.doflow/prompt-nudge`, `.doflow/prune` and `.doflow/scripts/` stay stageable. A `.gitignore` with other contents is yours and is never overwritten. DoFlow never edits the repository's own `.gitignore` or `.git/info/exclude`.

### Uninstall

When `doflow remove` removes the last harness of a scope it deletes that scope's control files: the ignore file (only when its bytes are DoFlow's), the throttle marker `upkeep-due`, the pass lock `upkeep.lock`, and the project's line in the user roots index. It prints `[INFO] Storage: removed <n> DoFlow control file(s)` when it removed any. The state itself and your `prune` and `prompt-nudge` files are left in place.

## Prompt nudge

A plain change request that names no `/do-*` skill can be suggested `/do`, once per session. The
suggestion is advisory: it never blocks or rewrites a prompt, and the model still does the task. The
decision's cost no longer grows with the prompt's length, and the hook stays near its existing 100 ms
budget on an idle machine; it is not free, so a slow machine can feel it.

- **Where.** Claude Code and Codex only, through the existing per-prompt hook
  (`core/harnesses/shared/hooks/policies/user-prompt-submit.sh`). The other six harnesses
  (Gemini CLI, Antigravity, OpenCode, Pi, Copilot CLI, Kiro) get no hook for this; Pi separately has
  a `tool_call` guard extension. Only the live-observed `cli-extension` pre-implementation gate row
  blocks; project-interactive and user-interactive coverage remains unknown, including interactive
  loading and project-trust behavior. These harnesses get only the
  rewritten `description` of `do`, `do-implement` and `do-flow`, which steer a plain change request
  to `/do` first.
- **When.** The first prompt of a session that reads as a code-change request: it starts with a
  change verb (after a polite lead-in such as "please") and names a code noun or a file path. The
  check is keyword-based, so it can miss a real request and can fire on a prompt that is not one,
for example a request to write a poem about a named function in a file.
- **When it stays silent.** Questions, slash commands, review and explanation requests, short
  replies such as "thanks" or "continue", prompts that mention `/do` or a `/do-*` skill, subagent
  prompts, a session whose branch already has a feature folder under `agent-docs/doflow/`, and a
  session where a `/do-*` skill has already run. A session is nudged at most once; a prompt that
  mentions `/do` also ends the chance for that session.
- **What it says.** One note, in the same hook output as the first-prompt context or alone on a
  later prompt. It tells the model to mention in one sentence that `/do` would classify the task and
  apply DoFlow's checks, then to do what the user asked, without running `/do` itself or waiting for
  a reply. It names `/do` and no other skill.
- **What it never does.** It makes no model call and no network call, stores no prompt text (the
  prompt reaches `jq` on standard input and is never written out), starts no `node` or `doflow-run`
  process, and never emits a `block` decision. Any failure on its path (no registry, no `jq` regex
  support, an unwritable state folder) leaves the prompt un-nudged.
- **Where the rules live.** Data, not code: the `promptNudge` object in
  `core/registry/workflows.json` (message, verbs, nouns, lead-ins, blockers, path pattern). The
  decision program is `core/harnesses/shared/hooks/policies/prompt-nudge.jq`. The workflow engine and
  the task classifier do not read this key; the registry shape guard G25
  (`test/guards/prompt-nudge-registry.test.js`) does.
- **How a rule change is judged.** `test/hooks/prompt-nudge.corpus.json` holds labelled prompts, some
  written with the rules in view and some without. `test/hooks/prompt-nudge.test.js` runs every one
  through the shipped rules: a prompt labelled silent that nudges fails the test, while recall on the
  prompts labelled as requests is printed as a diagnostic line and never asserted.

### Switching the nudge off

One setting file, `prompt-nudge`, holds one word on its first line (case and surrounding whitespace
are ignored):

| Scope | Path |
|---|---|
| Project | `<repo root>/.doflow/prompt-nudge` |
| User | `<config home>/prompt-nudge` |

| Value | Effect |
|---|---|
| `on` | the nudge may run (also the default when neither file exists) |
| `off` | no nudge |

When both files exist, the project file decides alone. A file that cannot be read, is empty, or holds
any other word counts as `off`. The setting affects only the nudge: the first-prompt context, the
session title and the other hooks are unchanged. The repo root is the nearest ancestor of the
session's working directory that holds a `.git` entry.

### First-prompt context on Claude Code

The same hook builds the first-prompt context: a Git block, up to 4,000 characters of the previous
compact summary, and a warning left by the prior session, plus a session title of the form
`branch — sha`. It now emits one nested `hookSpecificOutput` object for both Claude Code and Codex.
Claude Code ignores a top-level `additionalContext`, which is what the hook emitted before, so on
Claude Code this context was not delivered; it is now, once per session start (including after
compact, clear or resume). The hook emits the title in the form Claude Code documents; its rule is
to skip the title when the session already has one, and Codex never receives a title.

`DOFLOW_SESSION_ROLE=main|worker` (case-insensitive; unset or empty is `main`) declares a launched session's role in the environment the hook process inherits. A `worker` never writes the project's compact summary, receives no git context, summary or prior warning on its first prompt, never receives the `/do` prompt nudge, and does not write `uncommitted-warning.txt` when its session ends (session logging and the project's `last_active` time are still updated), so both files are left for the main session. Any other value is treated as `worker` and writes one `[doflow] unknown DOFLOW_SESSION_ROLE` line to stderr. A prompt carrying `agent_id` or `agent_type` (a native subagent) never claims the summary or warning. Whether a given harness forwards a launcher's environment to its hooks is not verified here.

## Git Lifecycle Intents

The `/do-git` skill provides cycle-aware commands:

- **start** - Begin a new task on the appropriate branch type
- **save** - Stage and commit with intelligent message from diff
- **sync** - Sync local branches with remote state
- **ship** - Ship current feature to integration branch
- **release** - Full release ritual: cut branch, bump version, merge to production, create tag
- **hotfix** - Create and propagate hotfix across all live lines
- **backport** - Cherry-pick a commit to another branch
- **status** - Report repository state and lifecycle position

Raw git operations still work via passthrough: `/do-git status`, `/do-git log --oneline`, etc.

The release version comes from `doflow-run git-state --next-version`. Its base tag is the highest `v*`
tag merged into HEAD or into the production branch, and the result carries a `warning` key when a
`package.json` exists and its version differs from that tag. A slug that is not letters, digits, dot,
underscore or dash (starting with a letter or digit, no `..`) is refused with exit 2 and
`{"error":"invalid-slug",...}`, by `doflow-run git-state --branch-name` and by `doflow-run paths` alike.

### Release checklist (beta cut)

1. Preflight: run `node src/release/preflight.ts`.
2. Rehearse: run `node src/release/rehearse.ts --node "$NODE22"` (resolve floor Node once via `NODE22="$(npx -y -p node@22.18.0 node -p process.execPath)"`).
3. Tag and push: create and push the release tag (`git tag v<version>` and `git push origin v<version>`). Tagging and pushing remain the user's explicit action.
4. Watch the workflow graph: the release workflow runs `preflight` and `test` in parallel, followed by `verify-artifact`, `draft-release`, `publish`, `verify-registry`, `promote`, and `publish-release`.
5. Verify and record: inspect `npm view @khoavu882/doflow dist-tags` and record the outcome in the cut record below.

#### Dist-tag policy

- `beta-candidate` holds a just-published prerelease until `verify-registry` passes and is empty otherwise.
- `beta` is the newest verified prerelease, moved only by `promote`.
- `latest` is moved only by the user (it points to `2.0.0-beta.4` now; UD-1 decides whether it follows each verified beta).
- A stable version is refused until the user decides stable (UD-3).

#### Rollback

Every rollback command is the user's:
1. Repoint the channel to the previous good version: `npm dist-tag add @khoavu882/doflow@<good> beta`
2. Remove a stale candidate: `npm dist-tag rm @khoavu882/doflow beta-candidate`
3. Deprecate the faulty version: `npm deprecate @khoavu882/doflow@<bad> "Superseded by <good>"`
4. Never unpublish a version.
5. Delete a draft Release left by a failed run: `gh release delete <tag> --yes`
6. Record the row in the cut record below.
