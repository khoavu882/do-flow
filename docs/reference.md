# DoFlow Skills Reference

## Quick Skill Reference

| Topic | Skills |
|---|---|
| Development cycles | `/do-flow "topic"`, `/do-brainstorm "topic"` |

## Full Skill Reference

Arguments below are transcribed from each skill's `argument-hint` (`/do-code-review` declares none;
its `[target]` is informal). G8 (`test/guards/reachability.test.js`) fails when a row here
documents a flag that the skill's `argument-hint` does not declare (one direction: a declared flag
missing from a row is not caught here). G10 (`test/guards/flag-index.test.js`) checks the hints
against [Flags](flags.md) both ways.

| Skill | Description |
|---|---|
| `/do [command\|request] [--depth shallow\|normal\|deep] [--estimate]` | Universal dispatcher, intent routing, tool capability selection, and estimation; `/do program <goal>` researches a programme-sized ask and hands you a checked roadmap draft |
| `/do-flow [feature description] [--from brainstorm\|design\|plan\|implement\|test\|review]` | Full-cycle development: brainstorm → design → plan → execute → test → code-review |
| `/do-brainstorm [topic/idea] [--intent <path>] [--depth shallow\|normal\|deep]` | Discover requirements through Socratic dialogue; seeds requirement.md in a branch-coupled feature dir |
| `/do-design [target] [--type architecture\|api\|component\|database]` | Design system architecture, APIs, and component interfaces; writes design.md |
| `/do-plan [--depth shallow\|normal\|deep]` | Generate implementation plan and dependency-ordered task checklist; writes plan.md |
| `/do-execute-plan [--scope next\|phase:N\|all\|resume] [--review] [--scaffold]` | Execute plan.md task checklist with specialist subagents and readiness gates |
| `/do-test [target] [--clean] [--watch]` | Execute project builds, automated test suites, and coverage verification |
| `/do-code-review [target]` | Code review automation: analyze complexity, risk, SOLID compliance, and code smells |
| `/do-implement [description of the change] [--from-review]` | Direct, standalone implementation from a description or `/do-code-review` findings — no chain artifacts required |
| `/do-git [intent] [args...] [--confirm]` | Cycle-aware git operations via named intents: start, save, sync, ship, release, hotfix, backport, status |
| `/do-constitution [principle inputs] [--amend]` | Create or amend the per-repo tier-2 constitution overlay and sync impact reports |
| `/do-diagnose [target\|issue] [--focus quality\|security\|performance\|architecture] [--fix]` | Unified diagnostics, root-cause investigation, and targeted code remediation |
| `/do-document [target\|query] [--type api\|guide\|impl\|index\|research] [--depth shallow\|normal\|deep]` | Unified technical documentation, architecture indexing, and deep web research |

| `doflow doctor [--json]` | Health check: harness adapters, capability providers, index freshness, and the project's detected build and test commands. Health means a provider **answered a probe**, not that its binary is on `PATH` — an installed provider that cannot answer reports `UNHEALTHY`, and one that declares no probe reports `UNVERIFIED`. Its `[Runtime Reach]` section lists, per installed harness and scope, whether the skills' resolver finds a dispatcher and runtime (`REACHED`, `NO-REACH` with the install command that fixes it, or `N/A`; in `--json`, `harnesses[].reach[]`). Reach is a static check of the installed files: it does not consider the other ways the dispatcher finds the CLI (`DOFLOW_CLI`, a `node_modules` install, a `doflow` on `PATH`). Two further sections report on MCP servers and never enter `[Warnings]` or `[Findings]` (in `--json`, `mcp.servers` and `mcp.consultations`). `[MCP Servers]` lists each server a shipped stage names and, per installed harness and scope, whether it is `selected` (in DoFlow's catalog selection), `configured` (present in the harness's MCP config, whoever wrote it), `not selected`, `not taken` (the harness takes no catalog servers; both only where DoFlow read every config the harness merges) or `unknown` (DoFlow cannot see every config the harness merges, as for Claude Code and Gemini CLI, or a config it reads could not be parsed, which prints `fix <file> first`), with the command that adds it where it is missing. `[MCP Consultations]` reads this project's orchestration journals (`.doflow/state/orchestration/`) and, per stage skill, counts the servers' outcomes over the 20 most recent recorded stage runs: `consulted, used`, `consulted, nothing usable`, `skipped`, `unavailable` and `no outcome recorded`, each in its own column, and, per server and skill, lists the latest 3 runs with no outcome after their count. Only runs that recorded MCP outcomes are counted, so a stage completed before this existed never shows as missing one. Finished orchestration journals are pruned 30 days after their work finished (see the `task-orchestration` row below), so the window counts only the runs still kept. `[Decision Model]` reports the optional local decision model; `[Advice Agreement]` summarizes recorded advisory picks and outcomes. These sections do not change the exit status. Doctor starts no MCP server: its MCP sections only read files, while provider probes run each declared probe command and an enabled decision model's endpoint is queried. When this doctor runs with `DOFLOW_UPKEEP=off`, it prints `note: DOFLOW_UPKEEP=off in this environment: upkeep and lifecycle retention are skipped`; `--json` adds `upkeepSwitch: "off"`, and neither appears otherwise. The adapter line of the text output reads `adapter PASS`; the JSON gains additive fields only. Exits 1 when a provider is installed but does not answer, or a harness has `NO-REACH`; neither MCP section changes the exit status The `[Warnings]` section (the `warnings` array in `--json`) also names a Node below the patched release of its line, 24.22.1 or 26.12.1 (CVE-2026-111497; kind `node-security-release`); it is a warning only, never a finding, and a line with no known patched release, such as Node 25 or 27, gets none. |

Exits 0 when enforced, 1 otherwise, or 2 for usage and unknown ids |
| `doflow readiness --task-class <class> --task-id <id> [--slug <name>] [--verification-plan <text>] [--scope <text>] [--invariants <text>] [--user-decision-pending] [--json]` | Evaluate a task's readiness contract. Classes: `bug`, `feature`, `refactor`, `trivial-edit`, `dependency-change`. Returns one of four states — `READY`, `NEEDS_EVIDENCE`, `NEEDS_USER_DECISION`, `BLOCKED` — never a number. The four trailing flags are inputs the **caller states** rather than evidence the gate measured, so they are reported straight back as `callerAsserted` (JSON) and `Caller-stated:` (text), and a requirement satisfied that way links no evidence. Every call records its evaluation, whatever its state, as the task's latest record under `.doflow/state/readiness/` (in a `<slug>/` subdirectory under the same rule as evidence, described below) and prints `Recorded:` with the path; `--json` adds `record` and `declaredScope`. A `--scope` that is a comma-separated list of repository-relative paths is also kept as the task's declared scope, which `verify` bounds a change by (`Declared scope:`); any other wording stays a statement. A previous record that cannot be read is moved to `<record>.unreadable` and a `Replaced:` line says so; a record written by a newer DoFlow is never replaced. The call exits 1 when it could not record the evaluation |
| `doflow evidence --task-id <id> [--slug <name>] [--action list\|add] [--kind <k>] [--provenance extracted\|inferred\|asserted] [--provider <p>] [--capability <c>] [--locator <file[:line]\|uri>] [--content <text>] [--need <intent>] [--absence] [--batch <file>] [--json]` | List a task's recorded evidence, or record it with `--action add`: one item from the flags, or a whole stage batch from `--batch` (a JSON array, or an object whose only key is `evidence`; `--batch -` or `--batch=-` reads stdin). Per item `kind`, `provenance` and `source` (`--provider` + `--capability`) are required and none is defaulted; `extracted` additionally requires a locator unless the item carries an observation (`--observed-command` and `--observed-exit`), `inferred` and `asserted` require content, and `generated-analysis`/`user-statement` may never be `extracted`. `--need <intent>` names exactly one declared intent and stamps `source.queryRef` from the task's current plan; without it the item remains unbound. `source.attemptRef` is read from the active task attempt. `--absence` requires `--need`, takes no locator, requires `extracted` provenance, writes `result: EMPTY`, and measures freshness from the provider's index at write time. Caller-supplied `queryRef` is refused with the fix to re-run using `--need`; `attemptRef` is refused with the fix to claim the task attempt and re-run without it; `result` is refused with the fix to use `--absence --need`. Absence without `--need` asks you to name the need, a locator asks you to drop it or record a positive item, and non-extracted provenance asks you to use `extracted`. Freshness is measured at the write and never accepted from the caller. A batch is validated whole, so one rejected item writes nothing. `--confidence`, `--score`, `--relevance` and every other score-shaped flag are refused by name: relevance is a property of a search, not of a fact |
| `doflow-run render-diagrams [--slug=<slug>] [--artifact=<path>] [--format=png|svg] [--json]` (`render-diagrams.sh`) | Render a chain artifact's fenced Mermaid blocks to image files, styled by the shipped theme. A **faithful** render: same nodes, same edges, same labels, and the committed Markdown is never modified. Output lands in `<feature dir>/design/diagrams/` and is excluded from version control by an ignore rule the verb writes on first run. Requires `@mermaid-js/mermaid-cli` on `PATH`, an optional dependency DoFlow never installs: when it is absent the verb reports how to obtain it and exits 0, because it sits outside the chain and must never make a missing optional capability read as a broken run. Runs only when a user invokes it, never as part of a stage, which is why no skill names it and `test/guards/verb-reachability.test.js` allowlists the verb |

| `bench impact-replay [--rev <ref>] [--commits <n>] [--json] [--out <path>]` | Offline replay that measures whether choosing tests from a change's imports would still catch what the full co-changed tests catch. For each of the last `--commits` non-merge commits reachable from `--rev` (`--rev` defaults to `HEAD`; `--commits` defaults to the `impactReplay.commits` value in `bench/config.json`), it exports the commit into a scratch directory with `git archive`, runs the commit's co-changed tests, restores the changed non-test files to their parent versions, runs the tests again to find the detecting set (a lower bound: only the co-changed tests are tried), and compares it with what `src/runtime/verification/impact.ts` would select. Makes no model call and touches no checkout. Prints one verdict: `insufficient-data` (fewer evaluated commits than the configured minimum), `keep-off` (a detecting test was missed, or the median selected fraction reached the ceiling), or `selection-candidate`. **The verdict enables nothing:** `verify` does not use the selector, and only this command reads `impact.ts`. `--out` sets the report path; the default is `bench/runs/impact-replay/<UTC stamp>.json`; `--json` prints the report |

It does not stop a write verb writing its own record or failure capture (`DOFLOW_FAILURE_CAPTURE`). If the one-time lifecycle store copy is still due, `followup`, `lifecycle`, `goal` and `failure --action settle --as imported` refuse with `store-migration-pending` (exit 1; nothing written). Doctor reports the switch only for its own environment |
| `DOFLOW_VERIFY_V0` / `<config>/verify-v0.off` | Verification V0 optimization flag (default `on`). Read once per verify invocation. When set to `off` (or when the `<config>/verify-v0.off` sentinel file exists; stat fault counts as absent/on), disables failed-first test execution and in-flight deduplication, recording `verify.run.v0="off"` |
| `DOFLOW_VERIFY_REUSE` | Can only turn verification reuse off. `off`, `0`, `false` or `no` disables reuse for the invocation even when the `verify.reuse` setting is `on` (see Settings keys); any other value, or none, leaves the setting in charge, so the variable never turns reuse on. Reuse ships off; see [Reuse of a recorded PASS](#reuse-of-a-recorded-pass) |

### Reuse of a recorded PASS

`verify` can answer a check from an earlier PASS instead of running it again. It ships **off**: turn it on by
writing `{"schema":1,"verify.reuse":"on"}` into `<config home>/settings.json` yourself (global-only; `config set` refuses it, as it refuses every security-relevant key; see Settings keys), and `doflow config -g` then shows `verify.reuse = "on"`. The environment variable
`DOFLOW_VERIFY_REUSE` can only turn it off.

- **What is recorded and reused.** Every level stores a check's PASS (a FAIL, an INCONCLUSIVE or a timeout is never stored)
  in the `verification-reuse` store (see Storage stores). Levels L1 and L2 look a stored PASS up; L3 (risk HIGH or
  CRITICAL) always executes its checks. A lookup refuses a record older than 24 hours, a record whose schema or payload
  digest does not match, and a record the key does not name. A stored output excerpt is bounded to 2,200 characters, so a
  reused check shows the same excerpt as the executed one; `truncated` and the log path are not kept for a reused check, so no log file exists for it. An executed non-PASS result for a key removes the stored PASS of that key while reuse is on, at every level.
- **The key.** A record answers a check only when its key is equal: the command, its timeout, the real working directory,
  `HEAD`, the digest of modified and untracked files, the sorted names of ignored entries, the bytes of the declared
  ignored inputs (`policy.reuse.ignoredInputs` in `core/registry/verification.json`), the identity (real path, size,
  modification time, inode) of `node` and of the command's first word on `PATH`, the Node version, platform, architecture
  and the environment digest. The digest of modified files also covers tracked files under `.doflow/` (except those under `.doflow/state/`), and the key covers the target of a tracked symlink that points outside the repository. A tree that cannot be keyed (git fault, over 500 modified files or 50 MB, an unreadable or
  linked declared input) runs unshared. A check is stored only when its inputs are the same after it ran as before.
- **How it shows.** A reused check is labelled `reused: {ref, recordedAt}` in the report, its telemetry entry says
  `shared: "reused"`, and the run record gains the `reused` count. The report counts gain `checksReused` when reuse is on; `checksRun` still counts every evaluated check, reused ones included. The text form prints `Checks: P/N passed (R reused, not executed)` when R is above 0 and a `reused <time> ref <ref>` line under the tier of each reused check.
- **Residual risk.** Reuse trusts the key, and the key does not see: network, time, external services or flaky tests; files outside the repository, such as `~/.npmrc`, the global git config or `<config home>` files; the contents of an ignored directory whose name is unchanged (`dist/`, `node_modules/`); ignored inputs other than those declared, which are read only at the git root, so a subpackage `.env` is not seen; untracked files under `.doflow/` or an in-repository config home, and any file under `.doflow/state/`, tracked or not; and the dependencies of a wrapper, such as `npm run`, `npx`, `env`, `exec`, `cd … &&` or `export PATH=…;`. A check is never reused when its command's first word or a leading `NAME=value` holds a quote, a backslash, `$` or a backtick, a leading assignment sets `PATH=`, or the first word starts with `~` or holds `*`, `?` or `[`; nor while any tracked symlink in the repository points at a directory, or at an unreadable or over-1 MB file, outside it (or the repository holds over 500 tracked links). A check that changes the files it reads is never stored; the check is compared on its state before and after the run only, so a check that changes its inputs and restores them during its own run, or leaves a process that does, is not detected. A process that cannot write the store does not reuse from it, because it could not remove a PASS after a failure. Reusing a producer check (a build) skips its side effects, so a later check that executes may fail spuriously. An executed failure removes the stored PASS only while reuse is on, so a PASS stored while reuse was on can be reused for up to 24 hours after reuse is switched on again, even if a FAIL ran in between with reuse off. Use reuse only for deterministic checks. The 24-hour limit and the off default bound the rest. The store trusts its own account: someone who can swap a directory above the store between a check and its lookup can already edit the source, so reuse does not defend against that.
  Turn reuse off with `"verify.reuse": "off"` in `<config home>/settings.json` or `DOFLOW_VERIFY_REUSE=off` when a run must execute everything.
- **Test selection is not wired in.** `verify` does not choose tests by impact. `bench impact-replay` (Runtime &
  Diagnostics Commands) only measures how such a selection would have done on past commits; its verdict enables nothing.

### Where a task's records live

`evidence`, `claim`, `readiness`, `context-pack`, `context-emit`, `research-request`, `outcome`,
`retrieval-plan`, `retrieve --scope code` (when it has a `--task-id` or `--slug`) and `orchestrate` read and write a
task's records in one root. Run from a linked worktree they always use the main checkout's
`.doflow/state` (the first entry of `git worktree list`), whatever folders the worktree holds, so one
task's records are never split across two stores and none is lost by `git worktree remove`. This also
holds for a project that tracks `agent-docs/`; before feature 115 a worktree was redirected only when it
lacked the feature folder. Delivery records (`delivery/`, written by `context-pack` and `context-emit`
alike) and the orchestration run follow the same root and the same namespace rule: the run of a task
id other than its feature's slug is `orchestration/<slug>/<task>.json`, the run of the feature itself
`orchestration/<slug>.json`. `render-audit` reads the run from the main checkout. A DoFlow sandbox
checkout (`.doflow-worktree-base` at its root) keeps its own store, and `-g` keeps the home store. Every
redirected call except `context-emit` prints one stderr note, `records are kept in the main checkout <root>`.

Source files stay in the checkout the verb runs in: `context-pack` and `context-emit` read the feature
folder, plan and pointers there, and a relative evidence `locator.file` is resolved and its freshness
hash taken there. Only a locator under `agent-docs/doflow/<slug>/` whose feature folder is absent from
that checkout and present in the main checkout is read from the main checkout; any other file missing
from the checkout is missing. Only the records move.

Records an earlier version left in the worktree's own `.doflow/state` are moved by one sweep on every
redirected call except `orchestrate --action list` and `status`, which only read, whatever task it names (or none). The stores swept are the ones
`core/registry/storage.json` lists with `src/runtime/state-root.ts` among their writers (evidence and
claims, delivery, readiness, research requests, outcome, retrieval plan, orchestration run), each with
its flat files and every `<slug>/` subdirectory, matched by file name exactly. Each file goes to the same
path in the main checkout, except that a flat record of a task id other than its feature's slug goes to
`<store>/<slug>/` (the slug it names, else the call's), where every reader looks. Under the target's lock
and then the source's, the source is read again (gone means another sweep moved it); equal bytes at the
target delete the worktree copy, and otherwise the bytes are written to a temporary file, renamed into
place, read back and compared before the worktree copy is deleted. Nothing is swept when the worktree's
`.doflow/state` is the main checkout's (a link to it), and a sweep where the worktree has no store
directory costs one `stat` per store. A file present in both checkouts with different bytes, a link on
either side's own path below the checkout, or a worktree file that is the main checkout's file itself
(the same device and inode) is left as it is and refuses the call with exit 2 and
`{"ok":false,"error":"store-conflict","adopted":[...],"removed":[...],"conflicts":[{"worktree":<file>,"main":<file>,"reason":"differs"|"link"|"same-file"}, ...]}`
(without `--json`, a stderr line, then one line per pair). Every pair is named, and the files the sweep
had already moved stay moved: keep one copy of each pair, remove the other and run the call again.

Readers that run from a linked worktree without the redirect (`verify`, and the edit hook) read the
main checkout's readiness record first; a copy at the same path in the worktree with other bytes
refuses, with the runtime's text `doflow gate readiness-before-implementation: task '<task>' has a
readiness record in this worktree (<file>) that differs from the main checkout's (<file>). Next: keep one
of the two and remove the other, then re-run. Nothing was changed.` (the hook exits 2). A record or run
an earlier version left in another worktree is still read from there when it is the one copy of this
feature's.

`doflow-run paths --json` carries one more key, `feature_root`: the checkout that holds
`agent-docs/doflow/<slug>`, the current checkout when it has the folder, else the main checkout when the
folder is only there, else the current checkout (a new feature, or a slug that names no feature).
`repo_root` keeps meaning the current checkout, and every emitted artifact path stays relative to it.
`validate` reads default targets, `render-audit` writes `audit.md` and the `decision` verb resolves the
feature folder under `feature_root`. `validate` also checks each `plan.md` with the `task-graph` rule:
one finding per problem `plan-check` reports (for example a duplicate task id, an unknown dependency or a
cycle). It prints one `note:` line on stderr and adds no finding when the dispatcher, Node or `jq` is
unavailable.

`--task-id` and `--task-class` are **required**, not defaulted. Readiness, evidence, claims and a
context pack all belong to one named task under one named contract; substituting `default` or
`feature` for an argument the caller omitted produces a confident verdict about a task or a
contract nobody asked about, which is exactly the failure mode the runtime is being corrected for.
Every refusal names the valid set.

An evidence `--kind` is one of ten: `exact-search`, `semantic-retrieval`, `structural`,
`historical`, `documentation`, `test-result`, `runtime-observation`, `user-statement`, `diff`,
`generated-analysis`. An unknown one is refused with all ten named. The ledger mints the record's
`id` and measures its `freshness`, so neither is accepted from the caller, and `supports` /
`contradicts` belong to `claim --action link`, which updates both sides of the relationship rather
than leaving a claim unaware of the evidence pointing at it.

Every command in this table is also a verb on the runtime seam — `doflow-run <verb>` — which is how
skills reach them. The two spellings run the same implementation; the seam additionally records a
metadata line in the run ledger.

`indicators` reads a different file from the three below it: the per-task orchestration records at
`<config>/state/orchestration/<slug>.json`, which the workflow orchestrator writes as stages complete.
That is why it is a separate verb rather than a mode of `stats` — a run-ledger record names no task,
stage or class, so no extension of `stats` could group by any of them. It reports per-stage intervals,
gate waits charged to no stage, recorded stage outcomes and rerun counts, grouped by task class, and it
prints what it cannot measure: anything needing git, pull-request or CI data, and the fact that a stage
figure is an interval since the previous recorded event rather than pure execution time. It writes
nothing.

`trace`, `stats` and `discover` read the run ledger at `<config>/state/runs/YYYY-MM-DD.jsonl`,
which `doflow-run` appends to once per dispatched verb. They locate it the way the dispatcher does
— nearest `.doflow` walking up from the working directory, or the global one — so they work from a
subdirectory. The walk passes over a `.doflow` inside another `.doflow` (a dispatch worktree's) and
continues to the project's store; that worktree `.doflow` used to hide the project store because the
launch writes the worker's delivery pack into its own `.doflow/state/delivery`. Records are metadata
only: a verb, a capability, a provider, an exit code, a
duration, counts and byte volumes. No argument value, command output or file content is recorded.
An empty ledger is a normal state and is reported as "no conclusion can be drawn", never as a
clean bill of health.

`inventory` reads neither the run ledger nor the orchestration record: it reads the two *ownership*
ledgers, one per scope, and derives everything else at read time. Nothing it reports is persisted.
Its optional positional is the project root (default the working directory) and `-t` restricts it to
named harnesses; the global scope's root comes from the process home directory and is not an
argument. Its report and `doflow reconcile` deliberately disagree about how much is repairable —
`reconcile` converges a scope onto what `doflow.lock` pins and names a harness the ledger holds and
the lock lacks — so the report states that gap as repair coverage rather than hiding it by adopting
the narrower definition. The modules behind it live under `src/runtime/inventory`.

`scaffold` resolves which feature is active the same way every chain skill does — from the working
directory, branch-derived in a git repo — so run it from the project root. Where a non-git root
holds more than one feature directory it cannot choose: it exits 2 naming every candidate, and
`--slug <name>` re-runs against the one you pick.

**Dense/rerank retrieval slots.** `core/registry/models.json` accepts an optional top-level `slots`
array binding a retrieval stage (`dense` embedding lookup, `rerank` cross-encoder pass) to one
declared provider: entries are `{ "id": "dense" | "rerank", "provider": <models.json provider id>,
"model": "<concrete model>", "enabled": false }`. A slot changes nothing until it is both declared
and `"enabled": true` — until then (and whenever the bound backend does not answer a PATH probe)
retrieval stays lexical BM25 plus the import graph, which remains the correctness floor. There is
deliberately no HTTP client here: enabling a slot only routes lookups to the named provider through
the same advisory availability probe `model-role` uses; the provider implementation itself (local
vs API) is a separate decision and no caller invokes one today. A malformed slot entry fails registry
load loudly; a `slots` value that is not an array is currently read as no slots (FU-7bnh0m).

Roadmap `next` holds `.doflow/state/roadmap/lease.json` for one call, keeps one record per run in

## Hook envelope and migration notes

Shipped hook bridges decode native events into envelope v1, call a canonical policy and render the harness's native response. The versioned coverage block in `core/registry/lifecycle.json` records policy, harness, event, profile and evidence; `doflow enforcement` reports what that evidence supports.

### Envelope, decision and diagnostics

Envelope v1 is the object under `doflow_event` in the native payload. It carries `version: 1`, the registry harness id, the native event name verbatim and a canonical operation; tool, paths, command, patch, correlation and identity fields appear only when the native input supplies them. `projectRoot` is reserved for a launcher and is never inferred from native `cwd`. Policies read v1 only; every other version is unsupported, and no native-field fallback remains. A direct policy caller must send v1 or pipe its native payload through `bash .doflow/shared/hooks/bridge/bridge.sh <harness> <event> <policy>`.

When `DOFLOW_DECISION_FD` names an open single-digit descriptor from 3 through 9, each policy writes a compact version-1 record on that descriptor: `v`, `policy`, `policyVersion`, `outcome` and `code`. The provisional allow record comes first; the last record determines the policy outcome. With the variable unset or an unusable descriptor, no record is written. Records contain no free text.

`DOFLOW_FAULT_PROFILE` selects `compat-1` (default) or `strict-1`; an unknown value uses `compat-1` and records `fault-profile-unknown`. Compat preserves each front door's current effect. Strict blocks faults for blocking policies, except Stop faults, which proceed under `strict-1`. Under `compat-1` a Stop fault keeps its door's old effect: Claude, Codex and Kiro Stop block on an unmarked exit 2, and Antigravity Stop blocks on an error that is not a signal. A real Stop deny blocks under both profiles (DEC-039). `DOFLOW_BRIDGE_TRACE`, when set to a file path, appends the bridge's decision object there; it is not model-visible. `DOFLOW_RUN_ID`, `DOFLOW_ATTEMPT` and `DOFLOW_TASK_ID` are reserved inputs for a launcher: in 077 they populate envelope identity or task fields when supplied and are otherwise absent. `DOFLOW_SESSION_ROLE` is normalized case-insensitively: unset or empty means `main`, `worker` means `worker`, and any other value emits a warning and is treated as `worker` by session policies; the envelope includes the role only when the supplied value is exactly `main` or `worker`.

Bridge diagnostics use the existing failure store and leave its storage declaration unchanged. Bridge failure-store points include `eval-error:exit-2-unmarked`, `eval-error:exit-<n>`, `eval-error:signal-<NAME>` (not SIGTERM, SIGINT or SIGPIPE), `bridge-spawn`, `bridge-timeout`, `bridge-missing`, `envelope-missing`, `contract-missing`, `envelope-encode` and `fault-profile-unknown`. The Antigravity runner records `runner-event-missing` when its event argument is missing or unknown. A `decision-mismatch` appears in the decision object and bridge trace only; it is a policy contract bug, not a failure-store point (DEC-028). Policies may record `unsupported:envelope-version`, `edit-without-target`, `dependency-missing:jq` and their existing policy-specific points. Diagnostic messages remain empty.

### Migration notes

The legacy native-field decoder has been removed. This is a breaking change for scripts that
pipe native payloads directly to a policy: update them to send a v1 envelope or use the bridge
command above. Input without a v1 envelope is out of step. The gate, bash and MCP policies deny
with `[<policy>] DoFlow hooks out of step; run: doflow update -t <harness>`; Stop and context
policies exit silently, with the prompt hook's `{}` no-op. If a door cannot load the bridge, it
uses a fixed native out-of-step response.

When an install or update changes shared hooks, it also refreshes outdated hook front doors for
other installed harnesses at that scope. Install/update plans report companion refreshes,
including harnesses the command did not name; dry-run lists them too. Edited
companion doors refuse the plan unless `-f` is supplied. The single backup includes companions,
and `doflow rollback <id>` restores them with the shared tree. On installs made before 077, Codex
and Gemini hook scripts have no ledger rows, so an edited script is replaced on the first update,
not refused. That update's backup keeps the edited copy for `doflow rollback <id>`; subsequent
edits are detected and refused. Antigravity shims are always overwritten and have no edited-door
check.

The Antigravity plugin bundle no longer declares hooks because its old entries pointed at files
the Antigravity projection does not install. Its skills, rules, agents and MCP configuration
remain available. The runner's unused Gemini-specific agent branch has also been removed.

Compared with the 0fcd973 front doors, the shared bridge intentionally changes these cases:

- A missing policy file is an evaluation error: `compat-1` proceeds and records a diagnostic; `strict-1` denies (DEC-025). Previously the shell's missing-file exit 127 could accidentally deny.
- The bridge captures policy output without a temporary file; an unwritable `TMPDIR` does not turn a gate deny into an allow. Background jobs close inherited bridge descriptors, so they do not hold Stop or SessionStart open. In `strict-1`, missing `jq` still produces the native deny; `compat-1` keeps its allow behavior (FX.1–FX.3).
- Codex `update -t codex -f` re-merges edited `hooks.json`, preserving user entries. Without `-f`, the conflict remains and the message gives a working remedy (DEC-040).
- A blocking evaluation error renders `[<policy-id>] DoFlow policy error; details: doflow-run failure list` on stdout (IC-013/DEC-019), rather than exposing raw policy or runtime stderr as the reason. Kiro PreToolUse and Stop doors use stderr for the fixed reason where their native contract requires it; Claude Stop retains its original exit code. Codex Stop crash stderr is suppressed (DEC-037).
- Context and advisory policy faults render nothing to the model and record a diagnostic (DEC-022).
- Codex `subagent-audit` now prints nothing for an error outcome; previously it printed `{}` when the policy failed.
- Kiro's agent-config event names (`agentSpawn`, `preToolUse`, `stop`) resolve to the same effects and native responses as their hook-config aliases (`SessionStart`, `PreToolUse`, `Stop`); the envelope retains the native event name.
- Antigravity's runner decodes its routed command, MCP and edit tools in the shared envelope path. Under RA1, `apply_patch` with `AbsolutePath` is now denied when design artifacts are absent; the legacy matcher allowed it.
- A policy terminated by a signal exits with status `128+n` (128 plus the signal number), such as `139` for SIGSEGV, on the session-context, user-prompt-submit, subagent-audit, Kiro PreToolUse and Claude Stop doors; Codex and Kiro Stop proceed with exit 0. A door whose fault blocks renders its native deny response instead.
- A missing v1 envelope or contract is an out-of-step state: gate, bash and MCP policies deny
  with the update command; Stop and context policies exit silently (DEC-032, DEC-033).
- A missing bridge file makes a shell door render its fixed native out-of-step response. The Pi
  extension blocks with the fixed native out-of-step reason; its coverage is blocking only for the
  live-observed `cli-extension` pre-implementation gate row. Project-interactive and
  user-interactive rows remain unknown; the live record does not establish interactive loading or
  project-trust behavior (DEC-036). The Antigravity runner applies this rule for a missing
  bridge under every fault profile: its gate denies and Stop stays silent (DEC-035).
- The bridge preserves a caller-set, non-empty `DOFLOW_AGENT`; otherwise it sets the harness id.

## Storage and retention

DoFlow prunes what it writes by default. A pass runs silently after a runtime verb (at most once a day per root), after `verify`, after `install` and `update`, and from the session hooks of harnesses that have them. It removes only entries of finished work past the bound in the table above, never open, waiting or unfinished work, stops after 750 ms or 5,000 removals and continues on the next pass. A pass never changes a command's output or exit status.

### Reading `doflow storage`

```bash
doflow storage                    # report: every store, its entries, size, bound and what a pass would remove
doflow storage --json             # the same as JSON, with the effective setting and the file that decided it
doflow storage --action prune     # run one pass now, ignoring the daily throttle
doflow storage -g                 # user and machine roots only
```

The report changes nothing on disk. It prints one line `Settings: project <on|off> (<file>|default); user <on|off> (<file>|default)`, naming the `settings.json` or legacy `prune` file that decided each setting, then one block per store: its `id`, `Location:`, `Entries: <n>; size: <bytes> bytes`, `Bound:` and `Would remove: <n>`, with up to 20 of those names followed by `... and <n> more`. `--action prune` prints the same and ends with `storage: removed <n> entries`. `--json` adds each store's `failed` entries, each with a `code`; `link-in-record-store` means a work record store holds a link, so log protection could not be checked and that pass removes no logs. `--action upkeep` is what the session hooks run: it prints nothing and always exits 0.

### Switching pruning off

`storage.prune` in the applicable `settings.json` decides whether pruning runs. Set it to `"off"` in `<project root>/.doflow/settings.json` for that project's stores, or in `<config home>/settings.json` for user and machine stores. A project value applies only to project roots. Use `doflow config list --show-origin` to see which file decides the value; `config` is read-only.

The legacy one-line `prune` files remain readable when the corresponding settings key is absent, and `doflow config list` reports them with a deprecation note:

| Scope | Path |
|---|---|
| project | `<project root>/.doflow/prune` |
| user | `<config home>/prune` |

The first line, trimmed and lowercased, must be `on` or `off`. For project roots the project file decides when present, else the user file; user and machine roots read the user file only. A legacy file that cannot be read, is empty or holds anything else counts as `off`; with neither settings key nor legacy file present pruning is `on`. For lifecycle-event retention, an explicit `DOFLOW_RETENTION_HOURS` takes precedence over `storage.retentionHours` in a settings file. If the environment value is unset, an explicit settings-file value still applies while pruning is off; with neither explicit value, the registry default applies only while pruning is on. An invalid `DOFLOW_RETENTION_HOURS` is reported as invalid and does not fall back. `storage --action prune` reports whether pruning is off and whether the explicit retention window removed lifecycle events. The report still lists what a pass would remove from other stores; for lifecycle events it lists only what an explicit environment or settings-file value would remove. The ignore file below is still written, and `existing` stores keep their own behaviour.

### The state ignore file

DoFlow writes `.doflow/state/.gitignore` (and `~/.doflow/state/.gitignore`) when the folder exists and holds no `.gitignore`:

```
# DoFlow runtime state: local to this machine, kept out of git by DoFlow.
# Removed by `doflow remove` when DoFlow leaves this project.
*
!/ledger.json
```

`git add -A` then stages nothing under `.doflow/state/` except `ledger.json`, while `.doflow/prompt-nudge`, `.doflow/prune` and `.doflow/scripts/` stay stageable. A `.gitignore` with other contents is yours and is never overwritten. DoFlow never edits the repository's own `.gitignore` or `.git/info/exclude`.

### Uninstall

When `doflow remove` removes the last harness of a scope it deletes that scope's control files: the ignore file (only when its bytes are DoFlow's), the throttle marker `upkeep-due`, the pass lock `upkeep.lock`, and the project's line in the user roots index. It prints `[INFO] Storage: removed <n> DoFlow control file(s)` when it removed any. The state itself and your `prune` and `prompt-nudge` files are left in place.

## Prompt nudge

A plain change request that names no `/do-*` skill can be suggested `/do`, once per session. The
suggestion is advisory: it never blocks or rewrites a prompt, and the model still does the task. The
decision's cost grows only linearly with the prompt's length (the whole prompt sees single regex scans, and only bounded
slices are lowercased), and the hook stays near its existing 100 ms
budget on an idle machine; it is not free, so a slow machine can feel it.

- **Where.** Claude Code and Codex only, through the existing per-prompt hook
  (`core/harnesses/shared/hooks/policies/user-prompt-submit.sh`). The other six harnesses
  (Gemini CLI, Antigravity, OpenCode, Pi, Copilot CLI, Kiro) get no hook for this; Pi separately has
  a `tool_call` guard extension. Only the live-observed `cli-extension` pre-implementation gate row
  blocks; project-interactive and user-interactive coverage remains unknown, including interactive
  loading and project-trust behavior. These harnesses get only the
  rewritten `description` of `do`, `do-implement` and `do-flow`, which steer a plain change request
  to `/do` first.
- **When.** The first prompt of a session that reads as a code-change request: it starts with a
  change verb (after a polite lead-in such as "please") and names a code noun or a file path. The
  check is keyword-based, so it can miss a real request and can fire on a prompt that is not one,
for example a request to write a poem about a named function in a file.
- **When it stays silent.** Questions, slash commands, review and explanation requests, short
  replies such as "thanks" or "continue", prompts that mention `/do` or a `/do-*` skill, subagent
  prompts, a session whose branch already has a feature folder under `agent-docs/doflow/`, and a
  session where a `/do-*` skill has already run. A session is nudged at most once; a prompt that
  mentions `/do` also ends the chance for that session.
- **What it says.** One note, in the same hook output as the first-prompt context or alone on a
  later prompt. It tells the model to mention in one sentence that `/do` would classify the task and
  apply DoFlow's checks, then to do what the user asked, without running `/do` itself or waiting for
  a reply. It names `/do` and no other skill.
- **What it never does.** It makes no model call and no network call, stores no prompt text (the
  prompt reaches `jq` on standard input and is never written out), starts no `node` or `doflow-run`
  process, and never emits a `block` decision. Any failure on its path (no registry, no `jq` regex
  support, an unwritable state folder) leaves the prompt un-nudged.
- **Where the rules live.** Data, not code: the `promptNudge` object in
  `core/registry/workflows.json` (message, verbs, nouns, lead-ins, blockers, path pattern). The
  decision program is `core/harnesses/shared/hooks/policies/prompt-nudge.jq`. The workflow engine and
  the task classifier do not read this key; the registry shape guard G25
  (`test/guards/prompt-nudge-registry.test.js`) does.
- **How a rule change is judged.** `test/hooks/prompt-nudge.corpus.json` holds labelled prompts, some
  written with the rules in view and some without. `test/hooks/prompt-nudge.test.js` runs every one
  through the shipped rules: a prompt labelled silent that nudges fails the test, while recall on the
  prompts labelled as requests is printed as a diagnostic line and never asserted.

### Switching the nudge off

One setting file, `prompt-nudge`, holds one word on its first line (case and surrounding whitespace
are ignored):

| Scope | Path |
|---|---|
| Project | `<repo root>/.doflow/prompt-nudge` |
| User | `<config home>/prompt-nudge` |

| Value | Effect |
|---|---|
| `on` | the nudge may run (also the default when neither file exists) |
| `off` | no nudge |

When both files exist, the project file decides alone. A file that cannot be read, is empty, or holds
any other word counts as `off`. The setting affects only the nudge: the first-prompt context, the
session title and the other hooks are unchanged. The repo root is the nearest ancestor of the
session's working directory that holds a `.git` entry.

### First-prompt context on Claude Code

The same hook builds the first-prompt context: a Git block, up to 4,000 characters of the previous
compact summary, and a warning left by the prior session, plus a session title of the form
`branch — sha`. It now emits one nested `hookSpecificOutput` object for both Claude Code and Codex.
Claude Code ignores a top-level `additionalContext`, which is what the hook emitted before, so on
Claude Code this context was not delivered; it is now, once per session start (including after
compact, clear or resume). The hook emits the title in the form Claude Code documents; its rule is
to skip the title when the session already has one, and Codex never receives a title.

`DOFLOW_SESSION_ROLE=main|worker` (case-insensitive; unset or empty is `main`) declares a launched session's role in the environment the hook process inherits. A `worker` never writes the project's compact summary, receives no git context or prior warning and never the `/do` prompt nudge or the default main lineage's summary (a launched worker can still receive a summary granted to it, or its own lineage's compact summary), and does not write `uncommitted-warning.txt` when its session ends (session logging and the project's `last_active` time are still updated), so both files are left for the main session. Any other value is treated as `worker` and writes one `[doflow] unknown DOFLOW_SESSION_ROLE` line to stderr. A prompt carrying `agent_id` or `agent_type` (a native subagent) never claims the summary or warning. Whether a given harness forwards a launcher's environment to its hooks is not verified here.

## Git Lifecycle Intents

The `/do-git` skill provides cycle-aware commands:

- **start** - Begin a new task on the appropriate branch type
- **save** - Stage and commit with intelligent message from diff
- **sync** - Sync local branches with remote state
- **ship** - Ship current feature to integration branch
- **release** - Full release ritual: cut branch, bump version, merge to production, create tag
- **hotfix** - Create and propagate hotfix across all live lines
- **backport** - Cherry-pick a commit to another branch
- **status** - Report repository state and lifecycle position

Raw git operations still work via passthrough: `/do-git status`, `/do-git log --oneline`, etc.

The release version comes from `doflow-run git-state --next-version`. Its base tag is the highest `v*`
tag merged into HEAD or into the production branch, and the result carries a `warning` key when a
`package.json` exists and its version differs from that tag. A slug that is not letters, digits, dot,
underscore or dash (starting with a letter or digit, no `..`) is refused with exit 2 and
`{"error":"invalid-slug",...}`, by `doflow-run git-state --branch-name` and by `doflow-run paths` alike.

### Release checklist (beta cut)

1. Preflight: run `node src/release/preflight.ts`.
2. Rehearse: run `node src/release/rehearse.ts --node "$NODE_FLOOR"` (resolve floor Node once via `NODE_FLOOR="$(npx -y -p node@24.22.1 node -p process.execPath)"`).
3. Tag and push: create and push the release tag (`git tag v<version>` and `git push origin v<version>`). Tagging and pushing remain the user's explicit action.
4. Watch the workflow graph: the release workflow runs `preflight` and `test` in parallel, followed by `verify-artifact`, `draft-release`, `publish`, `verify-registry`, `promote`, and `publish-release`.
5. Verify and record: inspect `npm view @khoavu882/doflow dist-tags` and record the outcome in the cut record below.

#### Dist-tag policy

- `beta-candidate` holds a just-published prerelease until `verify-registry` passes and is empty otherwise.
- `beta` is the newest verified prerelease, moved only by `promote`.
- `latest` is moved only by the user (it points to `2.0.0-beta.4` now; UD-1 decides whether it follows each verified beta).
- A stable version is refused until the user decides stable (UD-3).

#### Rollback

Every rollback command is the user's:
1. Repoint the channel to the previous good version: `npm dist-tag add @khoavu882/doflow@<good> beta`
2. Remove a stale candidate: `npm dist-tag rm @khoavu882/doflow beta-candidate`
3. Deprecate the faulty version: `npm deprecate @khoavu882/doflow@<bad> "Superseded by <good>"`
4. Never unpublish a version.
5. Delete a draft Release left by a failed run: `gh release delete <tag> --yes`
