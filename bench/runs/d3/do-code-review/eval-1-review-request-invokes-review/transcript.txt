--- ADJUDICATING THE ANALYZER OUTPUT (this is where the review became a review) ---
The generator's BLOCK is driven by 10 criticals. I opened the flagged files rather than passing the
number through, and every high-and-above finding in real source turned out to be a false positive
with a single shared root cause.

  $ grep -niE "password|api_key|secret|token|connection ?string" src/runtime/command-detect.js
      -> const TARGET_PATTERN_TOKEN = '{pattern}';    (a constant name, not a secret)
  $ grep -n "debugger" src/runtime/recovery.js
      -> a prose comment: "handing the task back to a debugger spends more of the budget"
  $ grep -nE "\.Result|\.Wait\(" src/adapters/kiro/index.js
      -> nothing. Case-sensitively, the C# pattern does not match this file at all.

ROOT CAUSE, verified: pr_analyzer.py:246 applies re.IGNORECASE to every RISK_PATTERNS entry, and
several of those patterns are case-significant C# identifiers.
  $ python3 -c "import re; p=r'\.(?:Result\b|Wait\(\)|GetAwaiter\(\)\.GetResult\(\))'; \
      s='const out = plan.result;'; print(re.findall(p,s,re.IGNORECASE), re.findall(p,s))"
    ['.result']  []
The same flag is why `TOKEN` matches the `hardcoded_secrets` pattern's literal `token`. One flag
explains the single critical in real source and 8 of the 12 highs.

Second issue found while checking coverage: 9 of the 10 criticals point into bench/runs/baseline/
and bench/runs/boundary/ — saved transcripts and .tap logs from PREVIOUS bench runs, which contain
those strings because they are records of earlier reviews discussing them. Nothing excludes
bench/runs/, so every eval run permanently inflates the critical count of every later review of this
repo. Directly relevant to D.4: this run's own outputs will do it again.

Third: I re-checked the THRESHOLDS dict as SKILL.md instructs. It holds exactly
long_function_lines, too_many_parameters, high_complexity, god_class_methods, max_imports. But the
checker emits `magic_number` (73 this run) and `commented_code` (8), neither in the dict nor in the
table, while SKILL.md flatly says "Those five are the whole set". max_imports has no emitter at all.
Obeying the contract's "do not report a threshold the analyzer does not implement" literally would
have meant suppressing 81 findings the analyzer genuinely produced.

--- WHAT SURPRISED ME / DID NOT WORK ---
1. do-code-review does not use the runtime seam at all. It has no doflow-run resolution step, and
   its documented script paths are skill-relative and unrunnable from the project root (FRICTION 1).
   Every other skill in this batch resolves $DOFLOW first. This one is the outlier and it is the one
   whose commands fail.
2. The deterministic tooling's high-severity output was, in this repository, almost entirely noise —
   and the noise was confident, specific, and mentioned ASP.NET in a repo with no C#. A reviewer
   following the generated report without opening files would have filed four bogus adapter bugs.
3. The BLOCK verdict is produced by a formula over counts with no false-positive path. Nothing in
   the pipeline lets a finding be dismissed, so the verdict cannot improve no matter what the
   reviewer establishes. The skill's Boundaries say it does "not replace human judgment on a Block
   verdict" — but there is no mechanism for that judgment to be recorded, so I recorded it in prose.
4. bench/runs/ contamination (F3) is a direct threat to this eval programme: every captured run
   makes the next review of this repo look worse.
5. code_quality_checker's per-file JSON key is `quality_score`, not `score`, and doc_quality_checker
   returns a bare list rather than an object with a summary — two different output shapes from two
   scripts in the same skill. Cost two failed parses.
