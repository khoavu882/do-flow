DECISION: ROUTE TO do-plan. The description contains a near-verbatim example of this prompt
("the user says 'turn this design into a plan'"), and the request asks for a breakdown to hand
to an implementer, not for a design and not for code. The competing candidates were ruled out
from their own descriptions: do-design writes design.md (the user says the design already
exists), do-implement writes code directly, do-execute-plan needs a plan.md that does not exist.
Confidence in the routing is high and it came from this description, not from the skill name.

Note on the description's precondition clause: it says "Use when requirement.md and design.md
already exist". Neither exists here. The clause reads as guidance on *when* the skill is the right
one, and the second half of the sentence ("or the user says 'turn this design into a plan'") is an
independent trigger, so routing still fires. This ambiguity is worth flagging: a stricter reader
could have declined to route because the stated precondition is unmet.

--- RUNTIME FRICTION OBSERVED ---
F1. Documentation/CLI mismatch on the claim link relation. EVIDENCE_LEDGER.md says to name
    "whether the relation is support or contradiction". The CLI rejects `--relation support`:
      "doflow claim: Invalid evidence relation 'support'. Allowed: supports, contradicts"
    A reader following the reference's own wording gets an error on the first try. `supports`
    works. Low severity, trivially fixable in either direction.
F2. That same rejection exits 0. The error text goes to output and the command reports success,
    so a script chaining `&& ` after a failed link would proceed as if it had linked. Contrast
    the ledger's own stated contract for a bad evidence id: "exit 2, naming the id".
F3. SKILL.md step 10 never mentions linking. Following the skill literally leaves every claim
    at status `hypothesis` forever, while EVIDENCE_LEDGER.md — which step 10 tells you to read —
    says a claim "becomes supported only through linked evidence". The skill's own two commands
    cannot produce a supported claim. This is a real gap between the skill and the reference it
    points at, not a misreading: five claims were added and all five came back `hypothesis`.
F4. `claim --action add` prints only the claim just added under a full table header, so the
    output looks like the complete claim set for the task when it is one row of five. Cosmetic.
F5. Claim ids restart at `_1` on each invocation (claim_msyhdj9k_1, claim_msyhdjc1_1, ...) —
    uniqueness comes from the timestamp prefix, so ids are unique but the `_1` suffix carries
    no ordinal meaning. Cosmetic, but it reads as if each add started a fresh store.
Nothing else failed. paths, classify, validate and evidence all behaved exactly as SKILL.md
describes, and the seam resolver found the runtime inside the sandbox on the first try.
