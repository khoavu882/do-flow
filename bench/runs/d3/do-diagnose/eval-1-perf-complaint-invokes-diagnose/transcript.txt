--- ROOT CAUSE ---
`npm test` wall time has a hard floor at the longest single test FILE, because `node --test`
parallelizes across files but runs the tests within a file serially in one worker.
test/cli-e2e.test.js is that floor: 46 tests, each spawning a real `node bin/doflow.js`, 41 of them
full installs, 14.2s in a single worker. The suite finishes in 15.4s — 1.2s more than that one file.
The user's perception is REAL but SMALL and its cause is not what it looks like: the suite went from
about 14.2s to about 15.4s this week (~8%), and that came from 24 new files finally exceeding the
idle capacity sitting under the long pole, not from any test getting slower. Nothing regressed.

--- RANKED REMEDIATION OPTIONS (produced, not applied — no --fix was passed) ---
1. Split test/cli-e2e.test.js into 3-4 files by lifecycle area (install / update+rollback / tools /
   multi-harness). Expected: wall time toward the ~9s floor, since the pole shortens and the pieces
   run in parallel across the 9 idle cores. Blast radius: LOW — moves test bodies, changes no
   source, and the guard suite does not constrain test file names inside test/.
2. Share one installed fixture across the read-only assertions in cli-e2e instead of doing 41 real
   installs. Expected: the largest absolute CPU saving. Blast radius: MEDIUM — shared state between
   tests is exactly what this file was written to avoid, and it risks trading 5s for a flake.
3. Do nothing, and set the expectation instead: an 8% rise from 24 new test files is the suite
   working. Blast radius: NONE. Named because the measurement genuinely supports it.
4. Raise node --test concurrency. Expected: NOTHING — H4 showed the box is at 2.2x of 10 cores.
   Listed only because it is the reflex fix and the evidence rules it out.
