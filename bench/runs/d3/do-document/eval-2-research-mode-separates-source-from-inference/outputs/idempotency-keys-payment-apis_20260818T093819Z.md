## Executive Summary

**[E]** There is a live standards effort: `draft-ietf-httpapi-idempotency-key-header-07`, an active
Internet-Draft of the IETF HTTPAPI Working Group, defines an `Idempotency-Key` request header as an
Item Structured Header (RFC 8941) whose value MUST be a String, and recommends a UUID or similar
random identifier.

**[E]** The dominant deployed pattern is the same shape everywhere: the **client** generates a
unique key, sends it on a `POST`, and the server stores the first request's outcome against that key
and replays it for any retry — Stripe saves "the resulting status code and body of the first request
made for any given idempotency key, regardless of whether it succeeds or fails," including `500`s.

**[E]** Where providers actually diverge is in four parameters, not in the concept: the **retention
window** (Stripe: keys may be pruned after 24 hours; Adyen: valid a minimum of 7 days), the **status
code for an in-flight duplicate** (Adyen: 422 or 409 with error 704; the IETF draft: 409), the
**status code for a key reused with a different payload** (IETF draft: 422; Stripe: documented only
as "errors"), and whether the key is scoped per-endpoint or per-account.

**[I]** The interesting design question has therefore moved off "should we accept an idempotency
key" and onto server-side execution: what happens when the request is interrupted *after* the server
has already mutated foreign state. That is the problem the `recovery_point` state-machine pattern
addresses, and it is not something a header spec can specify.

**[I]** A second shift visible across the sources is from idempotency-as-a-key-lookup to
idempotency-as-a-layered-property: key at the API boundary, dedup in queue consumers, unique
constraint in the database. No single cited source states this as a consensus; it is my reading of
the recurrence of all three layers across independent write-ups.

## 1. Is there a standard?

**[E]** `draft-ietf-httpapi-idempotency-key-header-07` is the most recent version, an active
Internet-Draft under the IETF HTTPAPI Working Group.
Locator: <https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/>

**[E]** Purpose, verbatim in substance: the header "can be used to make non-idempotent HTTP methods
such as POST or PATCH fault-tolerant." The key is "a unique value generated by the client which the
resource uses to recognize subsequent retries of the same request."
Locator: <https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-07>

**[E]** Format: "Idempotency-Key is an Item Structured Header [RFC8941]. Its value MUST be a
String." "It is RECOMMENDED that a UUID [RFC4122] or a similar random identifier be used."
Uniqueness "MUST be defined by the resource owner and MUST be implemented by the clients."

**[E]** Error semantics the draft defines:

| Condition | Draft's response |
| --- | --- |
| Key reused with a different payload | `422`, "Idempotency-Key is already used" |
| Key matches a request currently in flight | `409`, "A request is outstanding for this Idempotency-Key" |
| Missing / invalid key | `400`, body containing a link to relevant documentation |

**[E]** Expiry is deliberately left to the implementer: "The resource MAY require time based
idempotency keys to be able to purge or delete a key upon its expiry. The resource SHOULD define
such expiration policy and publish it in the documentation."
Locator: <https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.txt>

**[I]** That last clause is why provider retention windows differ so widely — the spec makes the
window a documented per-resource decision rather than a value to agree on. **Gap:** the draft is
still a draft; I did not establish whether any provider claims conformance to it, only that their
behaviour resembles it.

## 2. What the major providers actually specify

### Stripe — primary documentation

Locator: <https://docs.stripe.com/api/idempotent_requests>

**[E]** All of the following is quoted or paraphrased from that page:

- Transport: `-H "Idempotency-Key: KG5LxwFBepaKHyUD"` on the request.
- Generation: "A client generates an idempotency key… we suggest using V4 UUIDs, or another random
  string with enough entropy to avoid collisions."
- Length: "Idempotency keys are up to 255 characters long."
- Hygiene: "Avoid using sensitive data (for example, email addresses or personal identifiers) as
  idempotency keys."
- Replay semantics: Stripe saves "the resulting status code and body of the first request… regardless
  of whether it succeeds or fails. Subsequent requests with the same key return the same result,
  including `500` errors."
- Retention: "You can remove keys from the system automatically after they're at least 24 hours old.
  We generate a new request if a key is reused after the original is pruned."
- Payload mismatch: "The idempotency layer compares incoming parameters to those of the original
  request and errors if they're not the same to prevent accidental misuse."
- What is *not* saved: "We save results only after the execution of an endpoint begins. If incoming
  parameters fail validation, or the request conflicts with another request that's executing
  concurrently, we don't save the idempotent result because no API endpoint initiates the execution.
  You can retry these requests."
- Scope: "All `POST` requests accept idempotency keys. Don't send idempotency keys in `GET` and
  `DELETE` requests because it has no effect."

**[I]** The "we save results only after execution begins" rule is the subtle one and is easy to
implement wrongly: a validation failure and a concurrent-request conflict both leave the key
*unclaimed*, so the correct client behaviour is to retry with the **same** key, not to mint a new
one. The page says the request is retryable; the inference that the same key must be reused is mine.

### Adyen — primary documentation

Locator: <https://docs.adyen.com/development-resources/api-idempotency>

- **[E]** Header: `idempotency-key:<key>`.
- **[E]** Retention: "Idempotency keys are valid for a minimum period of 7 days after first
  submission."
- **[E]** In-flight duplicate: "If you submit a duplicate request before the first request has
  completed, the API returns an HTTP 422 – Unprocessable Entity or HTTP 409 - Conflict status with
  the error code 704: 'request already processed or in progress'."
- **[E]** Scope: applies to `POST` requests; `/payments` is given as the example. **Gap:** the page
  gives no exhaustive endpoint list.
- **[E] Explicit gap:** the page does **not** state what happens when a key is reused with a
  *different* payload. I am recording that as unanswered rather than filling it from Stripe's rule.

### Other providers — secondary sourcing only

**[E]** A secondary write-up characterises PayPal as enforcing uniqueness per API call type
(processing the first, rejecting simultaneous duplicates), Square as returning an error if the
payload changes with a reused key, and Modern Treasury as combining internal state machines with
external keys and retaining them for 24 hours.
Locator: <https://nxtbanking.com/idempotency-keys-payment-api-design/> (via search summary)

**Provenance caveat, stated rather than smoothed over:** these three are **not** verified against
each vendor's own documentation. They are second-hand and should be treated as leads, not as the
providers' specifications. I did not fetch PayPal, Square or Modern Treasury primary docs in this
pass.

### Cross-provider comparison (assembled by me from the rows above)

| | Header | Retention | In-flight duplicate | Different payload, same key |
| --- | --- | --- | --- | --- |
| IETF draft-07 **[E]** | `Idempotency-Key` | resource-defined, must be published | `409` | `422` |
| Stripe **[E]** | `Idempotency-Key` | ≥24h, then prunable | not saved; retryable | "errors" (code unstated on this page) |
| Adyen **[E]** | `idempotency-key` | ≥7 days | `422` or `409`, error 704 | **not documented** |

**[I]** The table itself is my synthesis; every cell is extracted, the act of aligning them is not.
Read across it and the practical consequence is that a client library cannot assume a status code —
it has to treat 409 and 422 as the same "retry later / do not mint a new key" class.

## 3. Contradiction found, and how it resolves

**[E]** A secondary source states that "Stripe returns a 422 error when the same idempotency key
appears with a different payload."
Locator: <https://dev.to/highflyer910/idempotency-keys-what-most-tutorials-dont-tell-you-1ncc> (via search summary)

**[E]** Stripe's own page says only that the layer "compares incoming parameters… and errors if
they're not the same." It names no status code.

**Resolution [I]:** these do not agree, and the primary source wins on what Stripe *documents*. The
specific value `422` matches the **IETF draft's** prescription, so the most likely explanation is
that the secondary author read the draft's code back onto Stripe, or observed it empirically. I am
recording `422` as **not established from Stripe's documentation**. A reader who needs the exact code
should observe it against the live API rather than trust either source.

## 4. Server-side implementation: the part the header spec does not cover

Locator: <https://brandur.org/idempotency-keys>

**[E]** The pattern stores an "idempotency key relation" in Postgres with `idempotency_key`,
`locked_at` (prevents concurrent work), `request_params` (for validation), and `recovery_point`.

**[E]** A **recovery point** is "a name of a check point that we get to after having successfully
executed any atomic phase or foreign state mutation." An **atomic phase** is "a set of local state
mutations that occur in transactions between foreign state mutations." **Foreign state mutations**
are external calls — to Stripe, Kafka, other services — beyond the application boundary.

**[E]** Phases advance through named recovery points (`started`, `ride_created`, `charge_created`,
`finished`) under serializable transactions, so an interrupted request resumes from its last point.
Intent is recorded locally *before* the foreign call, because "once we make our first foreign state
mutation, we're committed one way or another."

**[E]** Deferred work uses a "transactionally-staged job drain," and a separate **completer** process
discovers abandoned requests and pushes them to completion.

**[I]** This is the substantive answer to "current approaches," and it is a different question from
the header. A key-lookup cache gives you *replay*; the recovery-point machine gives you *resumption*.
Only the second one survives a crash between "charged the card" and "wrote the row" — which is the
failure a payment API actually has to survive. **[I]** The completer is the piece most home-grown
implementations appear to omit: without it, a client that disconnects mid-request leaves the key
locked until its TTL expires, and the retry hits the in-flight-conflict path rather than completing.
(That last consequence is my inference from the pattern's own mechanics, not a claim the article
makes.)

## 5. Adjacent and complementary approaches

All items below are **[E]** from a single secondary search pass unless marked otherwise.
Locators: <https://oneuptime.com/blog/post/2026-01-30-microservices-deduplication-strategies/view>,
<https://httptoolkit.com/blog/idempotency-keys/>, <https://dev.to/highflyer910/idempotency-keys-what-most-tutorials-dont-tell-you-1ncc>

- **Bind the key to a request fingerprint.** Store a hash of the body alongside the key rather than
  keying on user + operation alone, which catches a client recycling a UUID or a retry that mutated
  the amount.
- **Atomic create-if-not-exists storage.** A database unique constraint, or Redis `SET key value NX
  EX ttl`; the stated requirement is that whatever mechanism is used must be atomic.
- **Layered deduplication.** Idempotency keys at the API boundary for client retries, message
  deduplication in consumers for queue redeliveries, database constraints as a final safety net.
- **Design the operation to be idempotent instead.** `PUT /orders/{id}` rather than `POST /orders`;
  conditional updates; compare-and-swap / optimistic locking for race conditions.
- **Deduplication queues** for operations that cannot be made idempotent at all (the cited example is
  sending an email).
- **[E]** Response signalling: a header such as `X-Idempotent-Replay: true` lets a client distinguish
  a replayed response from a freshly computed one.
  Locator: <https://nxtbanking.com/idempotency-keys-payment-api-design/> (via search summary)

**[I]** "Use PUT instead" is not a peer of the others — it removes the need for a key on *update*
operations, but a payment authorization creates a resource whose id the client does not know in
advance, which is precisely the case PUT cannot cover. The sources list it alongside the others; I do
not think it belongs there for payments specifically.
