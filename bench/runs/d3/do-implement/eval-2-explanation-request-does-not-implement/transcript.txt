3. THE ANSWER (what I told the user)
================================================================
The location is decided in exactly two places, and nowhere else.

(a) The sandbox ROOT is fixed by the constructor, src/runtime/worktree.js:75-78:

      constructor(repoRoot, worktreesDir) {
        this.repoRoot = repoRoot;
        this.worktreesDir = worktreesDir || path.join(repoRoot, '.doflow', 'worktrees');
      }

    So it is a two-argument decision with a default: an explicit `worktreesDir` wins, otherwise
    `<repoRoot>/.doflow/worktrees`. The doc comment states the reason for that default —
    `.doflow/` is gitignored (confirmed: .gitignore line 51 is the bare entry `.doflow`), so
    sandboxes never surface as untracked noise in the parent tree. That is the whole rationale;
    there is no environment variable, no config file, and no registry lookup involved. `repoRoot`
    itself is not discovered by the class — it is whatever the caller passed in.

(b) The per-sandbox LEAF is fixed by pathFor, src/runtime/worktree.js:86-89:

      pathFor(taskId) {
        WorktreeManager.assertSafeId(taskId);
        return path.join(this.worktreesDir, taskId);
      }

    One flat directory per taskId — no nesting, no hashing, no uniquifying suffix. Same taskId
    always resolves to the same path, which is what makes reuse and idempotent removal possible.

    assertSafeId (line 79-84) gates it against SAFE_ID = /^[A-Za-z0-9._-]+$/ and throws
    "unsafe worktree id ... — allowed: letters, digits, dot, dash, underscore" otherwise. Since
    `/` is not in the class, a taskId cannot contain a separator, and `path.join` therefore cannot
    be walked out of worktreesDir. The guard is on the id, not on the joined result — a taskId of
    ".." would also be rejected only because... actually it would NOT be: ".." matches SAFE_ID
    (dot is allowed). `path.join(worktreesDir, '..')` resolves to the parent of worktreesDir.
    Flagging this as an observation from reading, not as a claim of an exploited bug: every caller
    in the tree passes a literal bench/task id, and the same id is also used to build a branch name
    `task/..` which git itself rejects. So it is unreachable in practice, but the id guard alone is
    not what makes the join safe.

The branch name is derived from the same id in lockstep, line 91-94: branchFor(taskId) returns
`task/<taskId>`. Path and branch are two functions over one id, never stored, which is why removal
(line 262-272) can reconstruct both from the id alone.

What DOESN'T decide the location, despite looking like it might:
  - create(taskId, baseRef), line 109-137, does not compute a path — it calls pathFor and then
    decides only whether to REUSE or RECREATE what is there. The reuse test is
    isRegistered(wtPath) (line 96-106), which parses `git worktree list --porcelain` and compares
    path.resolve'd strings. The comment there is explicit that "the directory existing on disk is
    not the same question" — a leftover directory git has forgotten is deleted with fs.rmSync and
    followed by `git worktree prune`, then recreated. So the path is stable across that whole
    branch; only its contents are not.
  - createSandbox(taskId, {baseRef='HEAD', ...opts}), line 257-260, adds nothing locational: it is
    create() plus projectSkills(), returning {path, manifest}. The doc comment says the split
    exists so non-evaluation callers can get a bare worktree without paying for a skill projection.
  - The two dotfiles written INSIDE the resulting path — `.doflow-worktree-base` (line 36, holds
    the base ref resolved to a concrete SHA) and `.doflow-skill-source.json` (line 42) — are
    consequences of the location, not inputs to it. Both are written inside the worktree for the
    stated reason that grading may run in a different process from execution.

Who passes what, in this repo:
  - bench/runner.js:388 embeds `new WorktreeManager(process.cwd())` in the dispatch plan — one
    argument, so the default `<cwd>/.doflow/worktrees` applies. This is why every bench sandbox
    lands at .doflow/worktrees/<case-id>/.
  - test/guards/evals.test.js:153 is the only caller that passes the second argument:
    `new WorktreeManager(REPO, tmp)` with tmp from fs.mkdtempSync — the guard projects skills into
    an OS temp dir precisely so the test does not create a real worktree under the repo. That
    caller is the evidence that the override parameter is load-bearing and not vestigial.

One-line answer: `worktreesDir` (constructor arg, defaulting to `<repoRoot>/.doflow/worktrees`
because that path is gitignored) joined with a `[A-Za-z0-9._-]+`-validated taskId — that is the
entire decision.
