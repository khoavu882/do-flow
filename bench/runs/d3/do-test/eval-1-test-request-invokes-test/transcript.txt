--- RUNTIME FRICTION OBSERVED ---
F13. `verify --action report` truncates each check's captured stdout at exactly 2000 characters
   FROM THE HEAD. For a TAP runner every useful thing — the `# pass` / `# fail` counts, the
   1..N plan line, and any failure diagnostic — lives at the TAIL, so the report retains the
   first ten passing subtests and discards the summary. SKILL.md step 5 requires reporting
   "pass/fail summaries, exact failure traces", and the runtime's own report cannot supply
   either for this repo's runner. Verified: stdout length is exactly 2000 for both checks, and
   the retained tail ends mid-word ("ok 10 - manife"). A tail-biased or head+tail capture would
   fix this. This is the most consequential finding of the case: a failing suite would produce a
   report naming the tier as FAIL with no visible trace.
F14. `targeted-tests` and `broad-tests` both compile to the identical command, `npm test`, so
   the whole suite runs twice — 34s wall for what is 17s of work. The contract even says why:
   "role 'testTargeted' needs a target pattern and none was supplied". Nothing dedupes two
   resolved checks that carry the same command, and no tier is marked SUBSUMED (a status the
   skill explicitly lists as possible). On a large repo this doubles verification cost for zero
   extra information.
F15. `maxRecoveryIterations` is present in the CONTRACT output (3) but absent from the REPORT
   output. SKILL.md step 2 asks for it to be reported, which works; but a caller that only has
   the report cannot see the retry bound the risk level set.
F16. The INCONCLUSIVE verdict is unavoidable for any run that was not preceded by an
   implementation stage in the same task id: change-scope is `required: true` at MEDIUM, and its
   only resolution path is a scope bound "declared before implementation". A plain
   "run the tests" request — exactly this eval's prompt — can therefore never return anything
   but INCONCLUSIVE, however green the suite is. That is arguably correct-by-design, but it
   means the verdict field carries no signal for the most common invocation of this skill, and
   the skill gives no guidance on saying so to a user who just asked what's broken.
F17. `verify --action report` exits 1 on INCONCLUSIVE. Per the dispatcher's own help, exit 1 is
   "an actionable finding", so this is consistent — but combined with F16 it means the ordinary
   happy path of do-test exits non-zero, which a wrapper script would likely read as failure.
No other friction. The seam resolver, paths, and both verify actions worked first try inside the
worktree sandbox.
