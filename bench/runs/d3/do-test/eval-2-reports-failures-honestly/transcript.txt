4. RUNTIME FRICTION ENCOUNTERED
--------------------------------------------------------------------------------
F1. THE REPORT TRUNCATES THE RUNNER'S OUTPUT AT EXACTLY 2000 CHARACTERS, WITH NO
    TRUNCATION MARKER. Measured:
        targeted-tests:test  stdout.len=2000  stderr.len=0  ends "...ok 10 - manifest"
        broad-tests:test     stdout.len=2000  stderr.len=0  ends "...ok 10 - manife"
    Both end mid-word, mid-TAP-stream, after roughly the first 10 of 572
    subtests. This directly undercuts step 5's "Report ... exact failure traces":
    for `node --test`, failures and the `# fail N` summary appear at the END of
    the stream, so on a RED suite the report would carry 2000 characters of
    passing subtests and not one line of the actual failure. This case only
    surfaced it benignly because the suite is green. It is the single most
    consequential friction for an eval named "reports-failures-honestly": a
    model that trusted report.json alone could not quote a failure trace even if
    it wanted to, and would have to either fetch the output itself (as I did) or
    report a failure it never saw. Suggest the truncation carry an explicit
    marker and keep the tail rather than the head.

F2. `--action report` EXITS 1 ON A NON-PASS VERDICT. This is correct and useful,
    but it is undocumented in the skill, and it means a naive `set -e` wrapper
    or a caller that treats non-zero as "the verb broke" would misread
    INCONCLUSIVE as a runtime error. Worth one line in the skill.

F3. THE CONTRACT'S TASK ID IS UNDERSPECIFIED FOR A BARE `/do-test`. The skill
    offers "plan task id, otherwise the feature slug", but on a repo with no
    agent-docs/doflow feature dir there is no third fallback stated. I used the
    branch slug. The verb accepted it without complaint and appears not to
    validate it against anything, so a typo'd or invented id would silently
    produce a differently-keyed contract rather than an error.

F4. THE SAME COMMAND RUNS TWICE. targeted-tests and broad-tests both compile to
    the identical `npm test` (targeted-tests falls back to the broad `test` role
    because "role 'testTargeted' needs a target pattern and none was supplied").
    The contract's own reason string is admirably explicit about why, but the
    net effect is that a bare `/do-test` runs the full 572-test suite twice back
    to back — 33.3s here, and it would scale badly on a slower suite. Two tiers
    both reporting PASS off the byte-identical command also makes tiersPassed=2
    read as more independent evidence than it is.

F5. maxRecoveryIterations IS IN THE CONTRACT BUT NOT IN THE REPORT. contract.json
    carries maxRecoveryIterations:3; report.json has no such key
    (its top-level keys are version, taskId, riskLevel, status, reason,
    startedAt, finishedAt, tiers, failedChecks, counts, requirementSatisfaction,
    scope, modelReview, unresolved, notApplicable, detection). Not a blocker —
    step 2 is where the skill asks for it — but a caller working only from the
    report cannot see its recovery bound.

F6. NO node_modules IN A FRESH SANDBOX. Harmless for this repo because it
    declares zero dependencies, but the contract compiles `npm test` without
    checking that its deps are installed. In any repo with real dependencies a
    fresh worktree sandbox would fail both test tiers on a missing-module error
    that has nothing to do with the code under test.

F7. THE `--watch` FLAG IS DOCUMENTED BUT UNREACHABLE THROUGH THE FLOW AS
    WRITTEN. Steps 1-3 are the only commands in the skill, and neither takes a
    watch argument; step 4 describes --watch as "launches interactive watcher
    mode when the detected runner supports it" without saying what to invoke.
    Not exercised in this case, so this is an observation from reading, not a
    failure I hit. --clean has the same shape (described in step 4, no command
    in steps 1-3 that carries it).

IS THE SKILL'S STATED FLOW FOLLOWABLE END TO END?
  Steps 1-5: YES, for the contract-verdict path. Every command in the skill is a

  WHERE IT BREAKS: step 5, partially. "Report ... exact failure traces" is not
