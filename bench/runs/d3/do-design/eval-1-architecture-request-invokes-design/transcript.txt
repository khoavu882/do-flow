FRICTION / SURPRISES
--------------------------------------------------------------------
F1. Description/body contradiction on the requirement.md precondition. The frontmatter says
    "Use when requirement.md already exists", which reads as a routing condition; SKILL.md
    step 3 makes the same precondition advisory and skippable. A dispatcher trusting the
    description would decline exactly the request this eval sends. The two should agree.
F2. EVIDENCE_LEDGER.md does not say the per-item field set is CLOSED. It names the required
    fields and then a "Refused by name" list, which implies anything not on that list is fine.
    The runtime refuses any field outside {kind, provenance, source, locator, content, taskId}.
    Cost me one full rejected batch. The error message itself is excellent — it named the item
    index, the offending field, and the accepted set — but the reference should state the
    closed set rather than only the refused one.
F3. Doc-vs-implementation mismatch on the link relation. EVIDENCE_LEDGER.md: "whether the
    relation is support or contradiction". The verb: "Allowed: supports, contradicts". Three
    calls failed on the noun form. One-word fix on either side.
F4. `doflow-run <verb> --help` does not print verb usage — it falls through to the installer's
    global `doflow` help (Usage: doflow <command> [path] [options], install/update/status/...).
    Combined with F2 and F3, there was no way to discover a verb's exact argument spelling
    except by triggering its usage error. `doflow-run --help` (no verb) does give a good verb
    list; the per-verb level is the gap.
F5. The claim store performs NO relevance check on a link. I linked claim 3 (the
    per-(intent_id, channel, attempt_no) keying claim) to ev_..._3, which is the ARTIFACT_FORMAT
    C4-diagram documentation item — genuinely unrelated. The ledger accepted it and flipped the
    claim from `hypothesis` to `supported`. Recording this against myself deliberately: the
    mis-link is in outputs/claims.json and I did not quietly repair it, because the finding is
    that "supported" is a link-count property, not a relevance property, and there is no
    `unlink` action to undo it (actions are add / link / list).
F6 (minor, environment). The Bash tool's shell is zsh, where `set -- $var` does not word-split.
    A loop I wrote to batch the link calls silently passed empty --evidence-id values; the verb
    caught it cleanly ("doflow: --evidence-id requires a value") but exited 0 through a pipe to
    head, so the failure was easy to miss. Not a DoFlow defect — noted because a skill that
    ships a shell loop over verb calls could hit the same thing.
F7 (positive). The runtime seam itself was solid: every verb (paths, classify, validate,
    evidence, claim) resolved through the walk-up on the first iteration against the sandbox's
    own .doflow/ and ran. The ship-runtime-into-.doflow fix is holding for Node-backed verbs in
    a real install.
