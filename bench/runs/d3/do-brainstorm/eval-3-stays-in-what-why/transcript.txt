--- WHAT SURPRISED ME / DID NOT WORK ---
1. The hardest judgement in this case had no runtime support at all: nothing in the skill, the mode
   file, or the runtime warns that the incoming request may itself be a solution rather than a need.
   The WHAT/WHY rule is stated as a prohibition on the OUTPUT ("Will Not: include tech detail"), not
   as an instruction to interrogate the INPUT. A less careful pass would faithfully write "FR-001:
   the system MUST cache dashboard queries" and violate the boundary while feeling compliant, and
   `validate` would pass it — the checker is a consistency checker and has no view on this. If D.3's
   prose rewrite wants this behaviour reliably, do-brainstorm's step 3 needs one line telling the
   reader to separate a proposed mechanism from the outcome it was proposed for.
2. Choosing the task class was genuinely ambiguous between `refactor` and `feature`, and the skill's
   step 2 gives no tiebreak — it just says name one class and the runtime validates it. The runtime
   ACCEPTS any of the eight valid ids without comment, so a wrong-but-valid class is never caught.
   I had to open core/registry/workflows.yaml myself to read the class descriptions; the `classify`
   verb returns them only for the class you already guessed. A `classify --list` that prints all
   eight descriptions would have made this a lookup instead of a source-reading exercise.
3. NFR-001's number is the artifact's weak point and the skill has no affordance for it. The
   requirement needs a testable target; discovery has no way to measure the baseline; the quality
   rules forbid invented metrics. I resolved it by stating the target AND labelling it in-line as
   chosen-not-measured plus an A1 assumption, but that is my own construction, not something the
   template or the skill offers.
4. Everything in the seam worked first time again: walk-up resolution, paths, classify, validate,
   evidence, claim add and claim link. Zero unexpected exits.
