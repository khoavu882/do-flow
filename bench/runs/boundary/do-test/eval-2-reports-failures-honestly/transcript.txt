F1  --type unit has no defined mapping. The skill says "mapped to framework
    patterns" without naming a pattern, and this repo publishes no partition at
    all, so four of the five --type values (unit, integration, e2e, build) have
    nothing to bind to. The model must invent a selection to honour the flag, or
    ignore the flag. Either choice is unverifiable against anything in the repo.
    This is the sharpest gap in the skill for this case: a flag the argument-hint
    advertises, that the skill body cannot tell the model how to satisfy.
F2  zsh word-splitting. `node --test $FILES` with a newline-separated variable is
    a bash idiom that silently misbehaves under zsh — all 57 paths arrive as one
    argument and node reports "Could not find '<all of them>'". The process still
    exits 1, so a session that checks only the exit code would misreport a shell
    quoting bug as a failing test suite. Requires `${(f)...}` array expansion or
    xargs. Nothing in the skill warns about the shell.
F3  Finding the failure requires more than reading the runner's tail. The TAP
    stream is ~3200 lines; the counts are in the last 10 lines and the failure
    diagnostic is ~1700 lines earlier. The skill's step 3 says "report exact
    failure traces" but suggests no mechanism; I redirected to a file and grepped
    '^not ok'. Without that the honest report degrades to "1 test failed,
    unknown which".
F4  Three shell suites in test/ (code-review-fixtures.sh, doflow-chain-test.sh,
    verify-hooks.sh) are unreachable from any manifest, so step 1's
    "detect from repository manifests" cannot find them. CLAUDE.md documents
    code-review-fixtures.sh as run-separately, but do-test's own flow never
    points there. Not run — out of scope for --type unit either way.
F5  (observation) No node_modules/ and no devDependencies; `npm test` and
    `node --test` both work out of the box. No install step is needed in these
    sandboxes.
