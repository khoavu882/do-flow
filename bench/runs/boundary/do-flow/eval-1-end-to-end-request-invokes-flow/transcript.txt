=== Reasoning ===
The description names the full chain explicitly: "brainstorm -> design -> plan -> implement ->
test -> review." The evaluated prompt, "Take this from idea to reviewed code: a webhook receiver
with signature verification," maps almost one-to-one onto that span:
  - "idea" == the discovery/brainstorm end of the chain (turning an unstructured idea into a
    requirement)
  - "reviewed code" == the terminal review stage of the chain (do-code-review), i.e. the user
    wants code that has gone through review, not just code that exists

The description's trigger clause is "Use when the user wants the entire spec-driven lifecycle to
run end-to-end without manually invoking each /do-* phase." The prompt does not name any single
phase (it doesn't say "just design this" or "just implement this") — it spans the full range from
idea to reviewed code in one request, which is precisely the "entire spec-driven lifecycle,
end-to-end, without manually invoking each phase" scenario the description calls out. It is
functionally equivalent to the description's own paraphrase examples ("just build this feature end
to end," "run the whole doflow chain for me") even though it does not use those exact words — the
semantic content (full lifecycle, single request, no phase-by-phase invocation) matches.

There is no competing, more specific trigger here: the prompt does not ask for one isolated phase
(e.g., only "design a webhook receiver" would route to do-design alone; only "implement signature
verification" would route to do-implement). Because the request spans idea -> reviewed code, the
full-chain skill (do-flow) is the correct match, not any single-phase skill.

Decision: YES — this prompt should route to do-flow.

=== Approval gates vs. straight-through ===
The frontmatter description itself states the chain runs "pausing only at defined approval gates"
— i.e., it does NOT run straight through unattended. The skill body (Behavioral Flow, steps 1-8)
confirms and elaborates this: it resolves state, proposes and validates a task class through the
runtime, announces the selection, runs stages in order, and explicitly "Stop[s] at the gates the
resolved workflow declares" (step 7), naming three gates for the `feature` workflow:
  - gate-0 (after discovery, conditional on unresolved clarification markers)
  - gate-a (after planning, before implementation — a conversational checkpoint on top of the
    hard `pre-implement-gate.sh` hook)
  - gate-b (after review, before handoff to /do-git)
Step 8 additionally states the chain must "Never skip a gate on an ambiguous answer." So: yes, the
description and body both imply approval gates are honored, not bypassed, during the chain.
