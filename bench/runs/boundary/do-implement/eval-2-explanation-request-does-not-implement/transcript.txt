THE ANSWER GIVEN (grounded in the read code)
=====================================================================
`WorktreeManager` decides a sandbox's location in two steps, and nothing else participates.

1. THE ROOT — chosen once, in the constructor (src/runtime/worktree.js:75-78):

     constructor(repoRoot, worktreesDir) {
       this.repoRoot = repoRoot;
       this.worktreesDir = worktreesDir || path.join(repoRoot, '.doflow', 'worktrees');
     }

   The second parameter is an explicit override; when it is omitted the root is
   `<repoRoot>/.doflow/worktrees`. The JSDoc immediately above states the reason for that default:
   the directory is gitignored, "so sandboxes never appear as untracked noise in the parent tree" —
   and `.gitignore:51` does indeed ignore `.doflow`. Both real callers exercise one branch each:
   `bench/runner.js:343` constructs `new WorktreeManager(process.cwd())` and takes the default,
   while `test/guards/evals.test.js:153` passes a tmp dir as the override, which is what lets the
   guard suite run without touching the real sandbox root.

2. THE LEAF — one join per task id, in `pathFor` (src/runtime/worktree.js:86-89):

     pathFor(taskId) {
       WorktreeManager.assertSafeId(taskId);
       return path.join(this.worktreesDir, taskId);
     }

   The path is `<worktreesDir>/<taskId>` — a flat directory per task, no nesting, no hashing, no
   uniquifying suffix. The same task id always resolves to the same path, which is what makes
   `create`, `remove`, `baseOf`, `collectDiff` and `withWorktree` able to find a sandbox again
   without storing a location anywhere.

   `assertSafeId` (lines 80-84) gates the leaf name against `SAFE_ID = /^[A-Za-z0-9._-]+$/` and
   throws on anything else. The comment at line 30 gives the reason: a task id reaches both a
   filesystem path and a git argument list, so it is "a potential argument-injection or
   path-traversal vector," and the code chooses to reject loudly rather than sanitise silently. A
   practical consequence: no `/` may appear in a task id, so a sandbox can never be nested one
   level deeper than the root.

WHAT DOES *NOT* DECIDE THE LOCATION, which is the part worth stating explicitly:

  - The branch name does not. `branchFor(taskId)` returns `task/<taskId>` (line 91-94), which
    carries a slash the path never does. Branch naming and path naming are two separate derivations
    off the same id.
  - The base ref does not. `create(taskId, baseRef = 'HEAD')` (line 112) uses `baseRef` only to cut
    the branch and to resolve the SHA it records; the path was already fixed by `pathFor`.
  - Prior state does not. `create` computes the path first, then reconciles reality to it: if git
    already registers that path as a worktree it is reused as-is (line 116); if a directory exists
    there that git does not know about, it is deleted and `git worktree prune` is run (lines
    118-121), because a leftover directory blocks `worktree add`. The location is never moved
    aside to avoid a collision.
  - `createSandbox` does not. It is a thin wrapper (line 257-260) that calls `create` and then
    `projectSkills`; the path it returns is `create`'s.

Two files land inside the chosen directory as harness bookkeeping rather than task content:
`.doflow-worktree-base` (the base SHA, written at line 135 — recorded as a resolved SHA precisely
because `HEAD` inside the worktree moves with every commit the task makes) and
`.doflow-skill-source.json` (the skill manifest, line 223). `collectDiff` filters both out of its
untracked list, so they do not read as task work.
