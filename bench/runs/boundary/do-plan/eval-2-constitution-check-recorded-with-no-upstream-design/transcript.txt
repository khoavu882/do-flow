*** FINDING F4 (the significant one) — the resolver's feature_slug is not a legal
    task id, on any slash-bearing branch. ***
`doflow-run paths --json` derives feature_slug from the branch name and returns
it with the separator intact. `evidence --task-id` (and by extension `claim`,
`context-pack`, `readiness`, `verify`, all of which key on the same id) rejects
any id containing a path separator. The skill instructs the model to use the
feature slug as the task id. Those three facts cannot all hold. This is not
specific to this sandbox's `task/` prefix — it breaks identically for the
conventional `feat/...`, `fix/...`, `chore/...` branches that DoFlow's own step 8
tells /do-plan to derive (`feat/<TICKET>-<slug-description>`). Any feature run on
a branch with a slash will hit this at the stage-boundary evidence write, i.e.
after all the real work is done. Neither the skill nor the resolver documents a
sanitisation rule, so every skill that hits this will invent its own — meaning
two skills in the same feature can silently key the same feature to two different
evidence records.
