### What sets the width of the range

- **Low end (~1 day):** the target harness closely resembles an existing shape — CLI tool with a
  file-based config, a skills-like extension mechanism, and either native MCP support or a clean
  "not applicable" (as `pi/index.js`'s own header comments show precedent for: it deliberately
  leaves MCP and hooks unimplemented because Pi's extension model doesn't fit DoFlow's shape,
  and that's an accepted, working design, not a gap to fill). Adapter code, one contract block,
  the up-to-11 assets.yaml edits, dispatch wiring, one new test file, and the 3-4 doc fixes fit
  in a single focused day.
- **High end (~2-3 days):** the target harness has no clean analog among the 7 (e.g., a
  fundamentally different trust/execution model like Pi's `pi.on()`-registered TypeScript
  handlers vs. DoFlow's shell-script hooks), forcing real research into that tool's actual
  on-disk format before any code is written, and/or the task includes the same "verify with real
  installs into scratch directories" step the copilot/kiro commit did — which is how 3 of the
  bugs in that precedent were found, not by writing mocks alone.

### Assumptions this estimate rests on

- **No target harness was named** in the prompt ("an eighth harness adapter" is abstract). The
  estimate assumes a harness of "typical" shape — comparable in surface area to the 7 that
  exist — not a best case or worst case. See "ASSUMPTION SUBSTITUTED FOR QUESTION" below.
- Solo engineer, uninterrupted, already has this repo's context loaded (excludes onboarding
  time).
- "The guard updates that keeps [it green]" is read as: the existing guard suite must still pass
  after the change, not that new guard *code* must be written — supported by G5/G9 both being
  data-driven over the registry rather than hardcoded to a harness list.
- Test-writing scope assumed to match precedent depth: one new `test/<harness>-adapter.test.js`
  in the 250-325 line band (matching `copilot-adapter.test.js`/`kiro-adapter.test.js`), not a
  broader integration-test buildout.

### Unknowns that would narrow this range

- Which harness is actually being targeted, and whether it has a documented, stable on-disk
  config format DoFlow can read without exploratory testing.
- Whether that harness has anything resembling MCP config and hook execution, or whether (like
  Pi) large parts of the six-function contract are legitimately no-ops for it.
- Whether "real installs into scratch directories" verification (as the copilot/kiro commit did)
  is in scope for this task or considered a follow-up.
- Whether `docs/capability-map.md`'s matrix needs a structural new column (larger doc edit) or
  the "seven" mentions are just prose that needs a word change.
