## Answer

`--prune <N>` has NO effect on `doflow remove`. It is parsed as a global CLI option (default value
0, in bin/doflow.js's option defaults), but only two commands actually consume it:

- `cmdInstall` (bin/doflow.js, around line 1023): after writing the install manifest, if
  `o.prune > 0` it calls `pruneBackups(backupRoot, o.prune)`.
- `cmdUpdate` (bin/doflow.js, around line 1105): same pattern, after an update run.

`cmdRemove` (bin/doflow.js lines 1113-1145) never reads `o.prune` and never calls `pruneBackups` —
`remove` doesn't create a backup in the first place (it only removes DoFlow-owned lifecycle
resources via `removeLifecycle`, printing a retention summary of what user-owned/shared files were
kept). So `doflow remove --prune 5` parses without error but the flag is silently a no-op for that
command.

Where `--prune` *does* apply (install/update), its behavior (src/backup.js, `pruneBackups`,
lines 156-173): it lists the backup directories under `backupRoot`, sorts them newest-first by
mtime, and deletes all but the `keepN` most recent — i.e. "keep only the N most recent backups,
delete the rest." The help text's one-line summary `--prune <N>  Keep only N most recent backups`
(bin/doflow.js ~line 877) describes this correctly, but is listed in the shared global "Options"
block of the help output, which makes it easy to assume (incorrectly) that it applies uniformly to
every command including `remove`. It does not.
