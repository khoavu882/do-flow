=== Assumptions substituted for questions ===
Per the non-interactive constraint, four design-level clarification questions that the skill's
step 5 would normally raise via AskUserQuestion (batched together, since all four are independent
of each other) were not asked. Each was decided directly and recorded in design.md section 8
(A1-A4) with a Basis of "User deferred" and Detail explaining what would change if the assumption
is wrong:

1. Question that would have been asked: "How should client applications submit events to the
   ingestion pipeline?"
   Options offered would have been: A) HTTPS REST API accepting batched JSON (recommended
   default) B) Client-embedded stream producer (direct Kafka/Kinesis produce) C) Host-based
   collector agent D) Decide for me
   Assumption chosen: (A) HTTPS REST API — most portable across web/mobile/server clients, avoids
   exposing broker endpoints to untrusted clients, matches the common analytics-collector pattern.

2. Question that would have been asked: "Should ingestion be one combined service or split into a
   public Collector + internal Processor?"
   Options offered would have been: A) Single combined service B) Split Collector + Processor
   (recommended default) C) Decide for me
   Assumption chosen: (B) Split — isolates the public attack surface from processing/scaling
   concerns and is what "analytics events" (implying real volume) usually warrants; also what
   makes a meaningful C2 Container diagram (2+ deployable units) rather than a single box.

3. Question that would have been asked: "Should a durable event stream buffer sit between the
   Collector and Processor, or should the Collector write to the warehouse synchronously?"
   Options offered would have been: A) Durable stream buffer (recommended default) B) Synchronous
   warehouse write, no buffer C) Decide for me
   Assumption chosen: (A) Durable stream buffer — decouples ingestion rate from warehouse write
   rate, enables replay/backfill, standard at any real event-ingestion scale.

4. Question that would have been asked: "How should event schemas be validated?"
   Options offered would have been: A) Versioned Schema Registry with compatibility enforcement at
   the Collector (recommended default) B) Best-effort/loose JSON validation C) Decide for me
   Assumption chosen: (A) Schema Registry — rejects malformed events at the edge (visible in the
   ingestion API's response) rather than letting bad data reach the stream/warehouse silently.
