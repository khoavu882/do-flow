---ASSUMPTIONS---
Every place AskUserQuestion would normally have fired during brainstorm/design and was instead
resolved by picking a reasonable default myself (all recorded in requirement.md §8 and design.md
§3 rationale text too):

1. Signature scheme: assumed a generic HMAC-SHA256 header-based scheme (default header
   `X-Signature-256`, value format `sha256=<hex>`, GitHub-webhook-style convention) rather than a
   named provider (Stripe/GitHub/Slack/etc.), because the prompt named no specific provider and
   this is the most reusable common denominator. Made the header name configurable so this is
   cheap to override later.
2. Stack: assumed plain Node built-ins (`http`, `crypto`) with zero new dependencies, rather than
   a framework like Express, because this repo's own package.json declares zero runtime
   dependencies and that is an explicit, load-bearing architectural trait of this codebase (a
   dependency-free Node CLI installer) — adding a framework for one unrelated feature would break
   that convention without being asked to.
3. Post-verification behavior: assumed the receiver hands the verified, parsed payload to a
   caller-supplied handler function and returns 200, rather than doing anything with the payload
   itself (persistence, forwarding, business logic), because no downstream behavior was specified
   and building one would be speculative (YAGNI).
4. Replay/timestamp protection: assumed it is out of scope for this iteration, because no
   threat model or timing requirement was given and adding it speculatively would violate the
   scope-discipline principle (P4) this repo's constitution states explicitly.
5. File/directory placement: assumed a new standalone top-level `webhook/` directory (with tests
   under `test/webhook/`) rather than inside `src/adapters/` or another existing architectural
   layer, because `src/` in this repo is specifically the DoFlow installer's own adapter/lifecycle
   machinery (per this repo's CLAUDE.md) and a generic webhook receiver is unrelated domain
   functionality that would misrepresent itself as a DoFlow capability if placed there.
