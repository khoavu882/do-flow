USER PROMPT:
What does the `--prune` flag do in doflow remove?

RESPONSE:

Short answer: nothing — `--prune` has no effect on `doflow remove`.

Looking at `bin/doflow.js`:

- `--prune <N>` is parsed as a global CLI option (`o.prune`, default `0`) and documented in the
  help text as "Keep only N most recent backups" (line ~152).
- It is only *consumed* in two places: `cmdInstall` (line ~275-278) and `cmdUpdate` (line ~357-360).
  In both, after a backup is created and the manifest is written, if `o.prune > 0` the code calls
  `pruneBackups(backupRoot, o.prune)` to trim old backups down to the N most recent.
- `cmdRemove` (line ~365-393) never reads `o.prune` at all. `remove` doesn't create a backup in the
  first place — it just resolves the lifecycle plan for the targeted harnesses and calls
  `removeLifecycle(...)` to delete DoFlow-owned native resources (preserving anything user-owned),
  then prints how many owned records remain. There's no backup-pruning step for it to hook into.

So if you pass `doflow remove --prune 5`, the flag is silently accepted (it's a recognized global
option) but has no observable effect — `--prune` only does something on `doflow install` and
`doflow update`, where it caps how many old backup snapshots are retained after a new one is made.
