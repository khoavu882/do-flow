Permissions
Kiro uses a capability-based permissions system that gives you fine-grained, declarative control over what the agent can do. You define rules per capability with match patterns and explicit effects, replacing older binary trust models.

Sandbox network rules
The

Shell command parsing
Shell commands are parsed before pattern matching. Compound commands (using
;
,
&&
,
||
,
|
) are split and each sub-command is evaluated independently. This prevents a rule for
npm test *
from accidentally matching
npm test ; curl attacker.com
.
The parser evaluates flags inside combined short options, so a command such as
grep -iP
still prompts when one of its flags requires approval. Options that can launch another program are never treated as read-only:
tar --use-compress-program
and
tar --to-command
require approval even when the base
tar
command is trusted.
In Kiro IDE 1.4.51 or later and Kiro CLI V3 sessions, Kiro blocks bash or PowerShell commands it cannot parse well enough to check against your permission rules. It asks the agent to rewrite the command instead of asking you to approve an unchecked command. Commands for
cmd.exe
still ask for approval. A rule that asks about every shell command still shows its normal prompt when no shell
deny
rule applies. An unconditional
allow
or
deny
rule still decides without parsing. If a valid command remains blocked after a few rewrites, the agent tells you it could not check the command.

Sub-agents
Kiro checks each sub-agent tool call against the parent session&#x27;s policy and the sub-agent&#x27;s own
permissions
. The stricter result wins:
A
deny
from either policy denies the call.
An
ask
rule in either policy prompts you.
If the parent session&#x27;s policy has no rule for the call, Kiro prompts you, even when the sub-agent&#x27;s own rules allow it.
A call that the sub-agent&#x27;s rules don&#x27;t mention follows the parent session&#x27;s policy. A sub-agent&#x27;s
allow
rules never grant more than the parent session allows. A
subagent
capability rule only controls whether a sub-agent can start without a prompt. See
Sub-agent permissions
.
Policy presets
Policy presets are named, composable sets of rules. Every preset except
approve-for-me
consists only of
allow
rules. A preset reaches a session by one of two paths, and the path decides its scope:
Requested by a client.
Any ACP client, including Kiro&#x27;s own surfaces and compatible third-party integrations such as editor integrations, review bots, and CI harnesses, can request the allow-only presets when it opens a session. Their rules are seeded at session scope and held in memory only.
Listed in a permissions file.
A preset named under
policies:
in a user or workspace
permissions.yaml
is expanded at that file&#x27;s scope and persists with the file. In Kiro CLI 2.36 or later, this is how the
approve for me
option under
/permissions
turns on
approve-for-me
: it writes the preset to the workspace permissions file.
approve-for-me
is the exception to allow-only. It adds an
evaluate
rule for every capability on top of a bounded set of
allow
rules, and it depends on Kiro&#x27;s trust classifier: when the classifier is unavailable, the preset contributes no rules and the session keeps asking. Turn it on with the
approve for me
option under
/permissions
in a Kiro CLI V3 session, where that option appears; see
Approve for me
.
How client-requested presets are applied
An ACP client requests presets in the
_meta.kiro.policyPreset
field of a
session/new
or
session/load
request. Multiple presets can be combined; their rules are merged as a union.
json
{
"_meta"
:
{
"kiro"
:
{
"policyPreset"
:
[
"edit-workspace"
,
"dev-shell"
]
}
}
}
Client-requested preset rules are seeded into the session when the client opens it, separately from the rules you configured in
permissions.yaml
. This is why a session&#x27;s active rules can include entries you never wrote.
Requesting an unknown preset ID rejects the session request. There is no silent fallback to a default policy.
Info
Client-requested preset rules are session-scope and held in memory only. On a cold session load (a full restart), the client must re-assert the preset. A session that resumes without a full restart keeps its already-seeded rules. A preset listed under
policies:
in a permissions file is not affected: it is read from the file at that file&#x27;s scope each time the file loads.

Choosing presets for a session
The allow-only presets remove prompts for the operations a session is meant to perform, and everything else keeps the default of asking for approval. Pick the narrowest profile that matches the session&#x27;s job.
approve-for-me
is not in this table: it is chosen under

Presets in embedded and headless clients
The same profiles map onto common integration patterns. An editor integration that embeds Kiro typically requests
edit-workspace
so in-workspace file edits do not prompt. A code review bot requests
read-workspace
and nothing more. A CI or evaluation harness driving the agent programmatically combines
edit-workspace
with
dev-shell
, then adds its own
deny

Warning
Headless execution raises the stakes: when no interactive client is available, every
ask
is treated as a deny, because the runtime has no interactive channel to deliver the prompt. A headless session can only perform operations that are explicitly allowed, so the presets it requests, plus any configured
allow
rules, define its entire grant surface.
