Model Context Protocol (MCP)
Section titled “Model Context Protocol (MCP)”
Antigravity supports the
Model Context Protocol (MCP)
, an open standard that lets AI agents and editors securely connect to local developer tools, databases, file parsers, and external remote APIs. This integration provides the AI model with real-time context and execution capabilities beyond your immediate workspace.
In this guide, you’ll learn how to connect and configure MCP servers across Antigravity products.
What is MCP?
Section titled “What is MCP?”
MCP acts as a universal bridge between Antigravity and your broader development environment. Instead of manually copying and pasting database schemas, logs, or API specifications into prompts or chat panels, MCP lets Antigravity fetch structured context directly or execute safe actions on your behalf when needed.
Add context
Section titled “Add context”
With MCP, Antigravity can use live data from connected MCP servers to inform its reasoning and suggestions:
When writing a SQL query, Antigravity can inspect your live Neon, Supabase, or AlloyDB schema to suggest correct table and column names.
When debugging deployment failures, Antigravity can pull recent build logs directly from Netlify or Heroku.
Add custom tools
Section titled “Add custom tools”
With MCP, Antigravity can execute specific, safe actions defined by your connected servers:
Create a Linear issue for a
TODO
item.
Search Notion or GitHub for authentication patterns.

MCP server timeouts
Section titled “MCP server timeouts”
By default, Antigravity waits up to 5 minutes for an MCP server to connect and list its tools, and up to 3 minutes for each tool call. A tool call that runs longer fails with an error that names the server and the limit, for example:
MCP tool call to server "sqlite-explorer" timed out after 3m0s
If a server’s tools need more time, set
timeoutSeconds
in that server’s entry:
A positive value, in seconds, replaces both limits. For example,
600
lets each tool call run for up to 10 minutes.
A negative value, such as
-1
, turns off both limits.
0
, or leaving
timeoutSeconds
unset, keeps the defaults.
Because the same value limits how long the server has to connect, a small value can stop a slow-starting server from connecting.
The following example lets each tool call on the
sqlite-explorer
server run for up to 10 minutes:
{
"mcpServers"
: {
"sqlite-explorer"
: {
"command"
:
"node"
,
"args"
: [
"/usr/local/bin/sqlite-mcp-server.js"
],
"timeoutSeconds"
:
600
}
}
}
Tool loading: lazy vs. eager
Section titled “Tool loading: lazy vs. eager”
Connected MCP servers can expose dozens of tools with large JSON schemas. Loading every tool definition into the model’s context window on every turn consumes tokens and increases latency, even when those tools aren’t used. To keep context usage low, Antigravity supports both
lazy
and
eager
tool loading.
Lazy loading (default)
Section titled “Lazy loading (default)”
By default, all enabled MCP tools are
lazy-loaded
:
Schema caching on disk
: When an MCP server connects, Antigravity writes each tool’s JSON schema (
name
,
description
, and
parameters
) to
&#x3C;app-data-dir>/mcp/&#x3C;serverName>/&#x3C;toolName>.json
(
~/.gemini/antigravity/mcp/&#x3C;serverName>/
in the Antigravity App and Antigravity IDE, or
~/.gemini/antigravity-cli/mcp/&#x3C;serverName>/
in the Antigravity CLI), along with an optional
instructions.md
file if the server provides instructions during initialization.
Compact system prompt
: Antigravity includes the exact
&#x3C;app-data-dir>/mcp/&#x3C;serverName>
directory path in the agent’s system prompt (so you don’t need to know the path for the agent to work) and lists each server’s tool names, grouped under
Eager
and
Lazy
, instead of full declarations.
On-demand invocation
: When the agent needs a lazy-loaded tool, it reads
&#x3C;app-data-dir>/mcp/&#x3C;serverName>/&#x3C;toolName>.json
to inspect the tool’s parameters and then invokes the tool through the built-in
call_mcp_tool
tool (passing
ServerName
,
ToolName
, and
Arguments
).
Eager loading
Section titled “Eager loading”
When an enabled tool is configured with
"eager": true
, Antigravity registers its full description and parameter schema upfront in the model’s native tool declarations as
mcp_&#x3C;serverName>_&#x3C;toolName>
(listed under
Eager
in the system prompt).
Direct invocation
: The agent calls
mcp_&#x3C;serverName>_&#x3C;toolName>
directly in a single turn without reading the schema file from disk or calling
call_mcp_tool
.
Higher token footprint
: Because the tool’s full schema is sent to the model on every turn, reserve eager loading for frequently used core tools where saving an extra file-read step outweighs the per-turn token cost.
Note
If Antigravity is unable to write a server’s tool schema files to disk during initialization, it automatically falls back to eagerly loading all enabled tools for that server.
Configure eager tools
Section titled “Configure eager tools”
To eagerly load specific tools from an MCP server, add a
tools
map to the server’s entry in
mcp_config.json
and set
"eager": true
for each tool you want pre-registered:
{
"mcpServers"
: {
"sqlite-explorer"
: {
"command"
:
"node"
,
"args"
: [
"/usr/local/bin/sqlite-mcp-server.js"
],
"env"
: {
"SQLITE_DB_PATH"
:
"/var/data/app.db"
},
"tools"
: {
"read_query"
: {
"eager"
:
true
},
"list_tables"
: {
"eager"
:
true
}
}
}
}
}
Any enabled tools on the server not listed with
"eager": true
remain lazy-loaded by default. Eager vs. lazy loading is evaluated after
enabledTools
and
disabledTools
are applied, so
"eager": true
only affects enabled tools; a tool marked
"eager": true
that is also in
disabledTools
, or missing from a non-empty
enabledTools
list, stays hidden.

OAuth
Section titled “OAuth”
Antigravity automatically handles OAuth 2.0 with Proof Key for Code Exchange (PKCE) for remote MCP servers that support
Client ID Metadata Documents (CIMD)
or
Dynamic Client Registration (DCR)
. For these servers, no additional client configuration is needed:
{
"mcpServers"
: {
"oauth-server"
: {
"serverUrl"
:
"https://api.example.com/mcp/"
}
}
}
When connecting to an OAuth-protected MCP server, Antigravity discovers the server’s Protected Resource Metadata (
/.well-known/oauth-protected-resource
, whose
resource
value must match the MCP server URL) and the first entry in
authorization_servers
(
/.well-known/oauth-authorization-server
or
/.well-known/openid-configuration
), then resolves client credentials in the following order:
Manual client credentials
: Uses
oauth.clientId
(and optional
oauth.clientSecret
) if specified in
mcp_config.json
.
Client ID Metadata Document (CIMD)
: Uses Antigravity’s hosted metadata URL as the
client_id
if the authorization server metadata includes
"client_id_metadata_document_supported": true
(for a few built-in integrations, Antigravity uses its own pre-registered client before trying CIMD).
Dynamic Client Registration (DCR)
: Registers a client dynamically if the authorization server metadata includes a
registration_endpoint
.
Client ID Metadata Document (CIMD)
Section titled “Client ID Metadata Document (CIMD)”
Antigravity publishes its OAuth Client ID Metadata Document at the following URL. In the Antigravity IDE, CIMD support requires version 2.6.0 or later:
https://antigravity.google/oauth/client-metadata.json
MCP servers and OAuth authorization servers can use CIMD to authenticate Antigravity clients without requiring dynamic client registration or manual per-user
clientId
setup:
Advertise
"client_id_metadata_document_supported": true
,
"code_challenge_methods_supported": ["S256"]
(PKCE is required), and a non-empty
issuer
in your authorization server metadata (
/.well-known/oauth-authorization-server
or
/.well-known/openid-configuration
).
When initiating the OAuth flow, Antigravity sends
client_id=https://antigravity.google/oauth/client-metadata.json
,
redirect_uri=https://antigravity.google/oauth-callback
, an
S256
PKCE challenge, and the RFC 8707
resource
parameter in the authorization and token requests.

https://antigravity.google/oauth/client-metadata.json
